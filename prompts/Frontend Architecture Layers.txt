# Frontend Architecture Layers — слои веб-клиента Rupor

База — feature-based архитектура, вдохновлённая Feature-Sliced Design (упрощённой). Принцип: каждая фича — самодостаточный вертикальный слайс; общие примитивы — в `shared/`. Все правила обязательны для агентов Claude.

## Корневая структура

```
web/
├── package.json
├── vite.config.ts
├── tsconfig.json
├── index.html
└── src/
    ├── app/         — корень приложения, провайдеры (Router, Zustand stores), глобальные стили
    ├── pages/       — page-компоненты, собирают features
    ├── features/    — независимые фичевые слайсы (auth, rooms, channels, chat, ...)
    ├── shared/      — переиспользуемые примитивы (api/, ui/, lib/)
    └── routes.tsx   — единая карта роутов
```

Других папок верхнего уровня в `src/` не создавать без согласования.

## Слои и направление зависимостей

Зависимости идут ТОЛЬКО вниз по списку. Обратные импорты запрещены.

```
app/        →  может импортировать из всего
pages/      →  features, shared
features/X  →  shared (НЕ features/Y)
shared/     →  только из стандартной библиотеки и npm
```

- `shared/` ничего не знает о `features/` и `pages/`. Если возникает соблазн сослаться на конкретную фичу из `shared/` — это сигнал, что код не shared.
- `features/A` НЕ импортирует напрямую из `features/B`. Если фичам нужно общаться — общая часть выносится в `shared/`, либо через store-события / app-слой.
- `pages/` собирает экран из `features/*` и не содержит бизнес-логики.
- `app/` подключает провайдеры (Router, Theme, глобальные store-провайдеры если нужны) и не содержит UI-логики экранов.

## Структура feature-слайса

Каждая фича — папка `web/src/features/{feature}/` со следующей структурой:

```
features/{feature}/
├── components/   — React-компоненты этой фичи
├── api/          — функции вызовов REST/WS, TS-типы DTO
├── store/        — Zustand-слайс(ы)
├── types/        — публичные TS-типы фичи (ViewModel, доменные)
├── hooks/        — кастомные хуки (опционально)
└── index.ts      — barrel re-exports того, что фича отдаёт наружу
```

- Слой `components/` — UI; делится на контейнерные и презентационные. Контейнер ходит в store; презентационный — только props.
- Слой `api/` — все обращения к бэку (REST + WS-команды), маппинг DTO ↔ ViewModel, error mapping.
- Слой `store/` — Zustand-сторы фичи; других глобальных state-механизмов нет.
- Слой `types/` — публичные типы фичи. DTO лежат рядом с api/, ViewModel — здесь.
- `index.ts` — то, что фича отдаёт наружу. Всё, что не реэкспортировано — внутреннее.

## Структура shared

```
shared/
├── api/
│   ├── fetch.ts    — единая fetch-обёртка с Authorization + auto-refresh
│   ├── ws.ts       — единый WS-клиент с reconnect и подписками
│   └── errors.ts   — типы ErrorEnvelope, ApiResult
├── ui/             — переиспользуемые UI-примитивы (Button, Input, Modal, Spinner, Toast, ...)
└── lib/            — чистые утилиты (форматирование дат, маска токена, валидаторы)
```

- `shared/api/` — единственное место голых `fetch()` и `new WebSocket()`. Фичи импортируют отсюда.
- `shared/ui/` — без бизнес-логики. Только пропсы → разметка.
- `shared/lib/` — pure-функции, без I/O.

## Pages и routes

- `pages/{Page}.tsx` собирает экран из features. Один файл — одна страница.
- `web/src/routes.tsx` — единая декларация роутов. Никаких «теневых» роутов внутри фичей.
- Гарды (требование авторизации, требование членства) — в `routes.tsx` или в shared, не дублировать в pages.

## App

- `app/App.tsx` подключает провайдеры в правильном порядке (Router → ErrorBoundary → ThemeProvider → Toaster, и т.п.).
- `app/main.tsx` — точка входа Vite, монтирует App в DOM.
- Глобальные стили — в `app/styles/` или `app/index.css`.

## Импорты

- Использовать алиас `@/` для путей от `src/`. Никаких `../../../../`.
- Алиас задаётся в `vite.config.ts` и `tsconfig.json` синхронно.
- Внутри фичи допустимы относительные импорты (`./components/Form`).

## Запрещено

- Импортировать из `features/A` в `features/B` напрямую.
- Импортировать из `features/*` или `pages/*` внутри `shared/*`.
- Создавать «универсальные» папки `utils/`, `helpers/`, `common/` верхнего уровня — это `shared/lib/`.
- Дублировать API-функции по фичам — каждый REST-эндпоинт вызывается из одного места.
- Дублировать ws-клиент / fetch-обёртку — они должны быть единственными в `shared/api/`.
- Класть Zustand-сторы вне `features/{feature}/store/` или `shared/`.
- Класть бизнес-логику в `pages/` — page собирает, не решает.
- Расширять `app/` бизнес-логикой — только провайдеры и роутинг.

## Что обязан проверить агент перед коммитом

1. Нет cross-feature импортов (`features/A` не тянет из `features/B`).
2. `shared/` не импортирует из `features/` или `pages/`.
3. Все обращения к API идут через `shared/api/fetch.ts` или `shared/api/ws.ts`.
4. Новый эндпоинт обёрнут одной api-функцией, нет дубликатов.
5. Структура новой фичи следует канону (`components/api/store/types/index.ts`).
6. Все новые роуты зарегистрированы в `web/src/routes.tsx`, не в фичах.

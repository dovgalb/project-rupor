# Clean Architecture — концептуальный справочник

Этот документ описывает, ПОЧЕМУ мы следуем Clean Architecture. Конкретные правила слоёв и директорий — в `Architecture Layers.txt`. Здесь — принципы и мышление.

## Цель

Код должен быть устойчив к изменениям внешнего мира. Смена БД, HTTP-фреймворка, протокола транспорта или формата сериализации не должна затрагивать бизнес-логику.

## Базовые принципы

1. **Независимость от фреймворков.** Бизнес-правила не знают про chi, sqlc, nhooyr/websocket. Фреймворк — деталь.
2. **Тестируемость.** Бизнес-правила тестируются без БД, сети, UI.
3. **Независимость от UI.** Можно поменять HTTP на gRPC без изменений в use case и domain.
4. **Независимость от БД.** PostgreSQL — деталь. Use case не знает, что данные лежат в SQL.
5. **Независимость от внешних агентств.** Домен не знает про сторонние API.

## Правило зависимостей (Dependency Rule)

Исходный код зависимостей указывает строго ВНУТРЬ. Ничто во внутреннем круге не может знать ничего о внешнем круге.

```
[ Frameworks & Drivers ]   <- cmd/server, pkg, драйверы БД, HTTP-сервер
   [ Interface Adapters ]  <- transport/http, repository/postgres
      [ Use Cases ]        <- usecase/
         [ Entities ]      <- domain/
```

Внутренние слои объявляют интерфейсы, внешние — реализуют. Это и есть инверсия зависимостей.

## Инверсия зависимостей — как это выглядит на практике

Use case нуждается в репозитории. Но use case не должен зависеть от postgres-пакета. Решение:

1. В `usecase/` объявляется интерфейс `UserRepository`.
2. В `repository/postgres/` пишется структура, реализующая этот интерфейс.
3. В `cmd/server/main.go` происходит склейка: создаётся реализация и передаётся в use case.

Use case не знает, что за ним — Postgres, моковая in-memory реализация или fake в тестах.

## Что считается бизнес-правилом

Бизнес-правило — это то, что было бы истинным, даже если бы у нас не было компьютера. Примеры:
- Пользователь не может зарегистрироваться с пустым именем.
- Сообщение не может быть длиннее 4000 символов.
- Только владелец комнаты может её удалить.
- Приглашение в комнату истекает через 7 дней.

Это всё идёт в `domain/`.

Не бизнес-правило:
- «Пароль хешируется через bcrypt» — это техническая деталь, живёт в адаптере.
- «JWT подписывается HS256» — деталь, живёт в адаптере.
- «Сообщение сохраняется в таблицу messages» — деталь, репозиторий.

## Use case vs Domain

- **Domain** отвечает на вопрос: «Что такое валидный X?» и «Какие операции допустимы над X?»
- **Use case** отвечает на вопрос: «Как выполнить сценарий A, используя X, Y, Z?»

Если логика касается одной сущности и её инвариантов — это domain. Если нужно оркестровать несколько сущностей, репозиториев и внешних зависимостей — это use case.

## Границы (Boundaries)

Каждый переход между слоями — это граница. На границе:
- Данные передаются в виде простых структур (DTO), не доменных сущностей, если это выходит за пределы приложения.
- Внутрь use case доменные сущности можно передавать напрямую.
- Наружу (в транспорт) — только DTO, чтобы транспорт не знал про domain.

Исключение: в маленьком проекте можно возвращать доменные сущности из use case в адаптер, если это не создаёт связности. Решаем по месту.

## Почему мы не используем ORM

ORM размазывает доменную модель по таблицам и тащит SQL-детали в домен (ленивая загрузка, теги, наследование от базового класса). Это нарушает правило зависимостей. Мы используем sqlc: SQL пишется явно, а домен остаётся чистым.

## Почему интерфейсы объявляются в потребителе

Go-идиома: интерфейс принадлежит тому, кто его использует, а не тому, кто его реализует. Use case говорит: «Мне нужно уметь сохранять пользователя», и объявляет `UserRepository`. Это позволяет менять реализации без изменения use case.

## Красные флаги

- В `domain/` появился импорт `database/sql`, `net/http`, `encoding/json`, сторонней библиотеки — СТОП.
- В `usecase/` появился импорт `transport/` или `repository/` — СТОП.
- Хендлер делает больше, чем парсинг + вызов + сериализация — скорее всего, бизнес-логика утекла в транспорт.
- Use case состоит из одного вызова репозитория — возможно, use case не нужен или модель неверна. Обсудить.
- «Антикоррозийный» слой на каждом шаге — оверинжиниринг. Инверсия зависимостей нужна на границе между слоями, а не внутри слоя.

## Что делать, если правило мешает

Clean Architecture — это инструмент, а не религия. Если строгое следование правилу рождает мёртвый код или абстракции без пользы — остановиться и обсудить с пользователем. Лучше один раз нарушить осознанно, чем плодить бессмысленные обёртки.

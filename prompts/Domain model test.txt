# Тесты доменной модели

Доменный слой — это место, где тесты самые важные и самые дешёвые. Никаких моков, никакой БД, никакого HTTP. Только чистые функции и структуры.

## Принципы

1. **Без моков.** Domain не имеет внешних зависимостей, мочить нечего.
2. **Без фреймворков.** Используем стандартный `testing`. Никаких testify, ginkgo, gomega без согласования.
3. **Чёрный ящик.** Тестируем поведение через публичный API сущности, а не внутренние поля.
4. **Быстро.** Миллисекунды на сотни тестов. Если тест доменной модели идёт дольше 10мс — что-то не так.
5. **Независимость.** Тесты не зависят друг от друга, порядок не важен.

## Что именно тестируем

1. **Конструкторы и инварианты.** Что `NewX` отвергает невалидные входы и возвращает конкретную доменную ошибку.
2. **Методы бизнес-операций.** Что метод меняет состояние корректно и возвращает ошибку в запрещённых сценариях.
3. **Value objects.** Что валидация работает, нормализация (trim, lowercase) применяется.
4. **Методы-запросы.** Что `CanPostIn`, `IsOwnerOf` и подобные возвращают ожидаемый ответ.
5. **Неизменность в случае ошибки.** Что провалившийся метод не оставил сущность в мутировавшем состоянии.

## Что НЕ тестируем в domain-тестах

- Сохранение в БД (это репозиторий).
- HTTP-коды (это транспорт).
- Оркестрацию use case.
- Форматы сериализации.

## Структура теста

Используем table-driven тесты везде, где проверяем варианты входов. Для одиночных сценариев — обычный `t.Run`.

```go
func TestNewEmail(t *testing.T) {
    t.Parallel()

    cases := []struct {
        name    string
        input   string
        want    string
        wantErr error
    }{
        {"валидный", "user@example.com", "user@example.com", nil},
        {"с пробелами — триммится", "  user@example.com  ", "user@example.com", nil},
        {"верхний регистр — опускается", "USER@Example.COM", "user@example.com", nil},
        {"пустая строка", "", "", domain.ErrInvalidEmail},
        {"без @", "userexample.com", "", domain.ErrInvalidEmail},
    }

    for _, tc := range cases {
        tc := tc
        t.Run(tc.name, func(t *testing.T) {
            t.Parallel()
            got, err := domain.NewEmail(tc.input)
            if !errors.Is(err, tc.wantErr) {
                t.Fatalf("NewEmail(%q) err = %v, want %v", tc.input, err, tc.wantErr)
            }
            if err == nil && got.String() != tc.want {
                t.Fatalf("NewEmail(%q) = %q, want %q", tc.input, got.String(), tc.want)
            }
        })
    }
}
```

## Именование

- Тест-файл лежит рядом с тестируемым файлом: `user.go` → `user_test.go`, в том же пакете `package domain` (белый ящик) или `package domain_test` (чёрный ящик). По умолчанию — чёрный ящик (`domain_test`), чтобы тесты зависели только от публичного API.
- Функция: `TestTypeName_MethodName` или `TestFuncName`.
- Подтесты в `t.Run`: короткое описание сценария на русском или английском, единообразно по проекту.

## Хелперы

Если несколько тестов создают одинаковую сущность — завести фабрику в `domain/testing_fixtures_test.go` или `*_test.go`:

```go
func newTestUser(t *testing.T) *domain.User {
    t.Helper()
    u, err := domain.NewUser(
        domain.NewUserID(uuid.New()),
        mustEmail(t, "test@example.com"),
        mustUsername(t, "tester"),
        time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC),
    )
    if err != nil {
        t.Fatalf("newTestUser: %v", err)
    }
    return u
}
```

`t.Helper()` обязателен, чтобы ошибки показывали правильную строку вызова.

## Детерминизм

- Никаких `time.Now()` внутри тестируемого кода — время передаётся снаружи. В тестах передаём фиксированный `time.Date(...)`.
- Никаких `rand` без явного источника.
- Никаких `uuid.New()` в тестируемом коде, если результат сравнивается — идентификаторы передаются в конструктор извне.

## Проверки

- Для ошибок — `errors.Is` (или `errors.As` для типизированных).
- Для значений — явное сравнение через `!=` и `t.Fatalf` с информативным сообщением.
- Не использовать `reflect.DeepEqual` для сравнения сущностей с приватными полями — сравнивать через геттеры.
- Для сложных структур можно использовать `go-cmp`, если будет согласовано.

## Что должно быть в тесте на бизнес-операцию

Пример: `Room.TransferOwnership(newOwnerID)`.

1. **Успех:** старый владелец — один, новый — другой, оба участники комнаты, метод возвращает nil, `room.OwnerID()` стал новым.
2. **Новый владелец не в комнате:** метод возвращает `ErrUserNotMember`, состояние не изменилось.
3. **Новый владелец уже владелец:** метод возвращает `ErrAlreadyOwner` (или идемпотентен — решение на этапе проектирования), состояние как было.
4. **Комната удалена:** метод возвращает `ErrRoomDeleted`.

Для каждого негативного сценария проверяем: ошибка та, что ожидается, И состояние сущности не изменилось.

## Параллельность

- `t.Parallel()` в каждом тесте и каждом подтесте.
- Тесты domain-слоя не делят общее состояние — параллельность безопасна.
- Не забывать `tc := tc` в цикле перед `t.Run`, иначе замыкание захватит последнюю итерацию.

## Покрытие

- Покрытие — инструмент, а не цель. 100% покрытие, которое ничего не проверяет, бесполезно.
- Обязательно покрыть: все ветки конструктора, все ветки бизнес-операций (успех + каждая доменная ошибка), все граничные случаи value objects.
- Цель — чтобы любая регрессия в инвариантах домена падала в тестах.

## Красные флаги

- В domain-тесте импортируется `net/http`, `database/sql`, `testify/mock` — СТОП.
- Тесту нужен setup с запуском чего-либо (БД, сервер) — это уже не domain-тест.
- Один тест проверяет несколько несвязанных вещей — разбить.
- Тест зависит от текущего времени — сломается завтра.

# React Components — как писать компоненты в проекте Rupor (web/)

База — React 18, без классовых компонентов. Все компоненты — функциональные. Все правила обязательны для агентов Claude.

## Общие принципы

- Один компонент — одна ответственность. Если файл превысил ~200 строк — кандидат на разбиение.
- Презентационные и контейнерные — разделять. Контейнер ходит в store, презентационный получает props.
- Не больше 5 props у презентационного компонента (rule of thumb). Если больше — группируй в объект или дроби компонент.
- Никаких inline-функций в JSX, если они пересоздаются на каждый рендер И передаются мемоизированным детям — выноси через `useCallback`.

## Сигнатура

```tsx
type LoginFormProps = {
  onSubmit: (values: LoginValues) => Promise<void>;
  isSubmitting: boolean;
};

export function LoginForm({ onSubmit, isSubmitting }: LoginFormProps) {
  // ...
}
```

- Тип props — `*Props`, всегда `type` (не `interface`).
- Деструктуризация props сразу в сигнатуре.
- `export function` declaration, не `const Foo = () => ...` — лучше дебажится, лучше HMR.
- Default-экспорты запрещены. Только named exports.

## Состояния UI (обязательны все)

Любой компонент, который зависит от async-данных или ввода пользователя, рендерит ВСЕ применимые состояния. Пропуск состояния = REJECT.

| Состояние | Когда | Как |
|-----------|-------|-----|
| `idle`    | до старта операции | стартовый UI |
| `loading` | операция в процессе | спиннер / скелетон |
| `empty`   | операция успешна, но данных нет | placeholder с CTA |
| `error`   | операция упала | сообщение с возможностью retry |
| `success` | операция успешна, данные есть | основной UI |
| `disabled`| форма / кнопка временно недоступна | визуально отличается от enabled |

Каждое состояние должно быть покрыто тестом (см. `Tests Style (Web).txt`).

## Хуки

- Кастомные хуки — `useXxx`, в `features/{feature}/hooks/` или `shared/lib/`.
- Один хук — одна ответственность.
- Не вызывать хуки условно. Не вызывать в циклах.
- Зависимости `useEffect` / `useMemo` / `useCallback` — все, что используются внутри. ESLint-правило `react-hooks/exhaustive-deps` — обязательно включено.
- `useEffect` для побочных эффектов (подписки, таймеры, имperative DOM). НЕ использовать для трансформации данных — для этого `useMemo` или производное в селекторе store.
- Возвращать из `useEffect` функцию-cleanup всегда, когда есть подписка / таймер / event-listener.

## Формы

- Стратегия форм выбирается в `03-decisions.md` фичи: либо контролируемые компоненты вручную, либо `react-hook-form` + `zod`.
- В рамках одной фичи — НЕ микшировать обе.
- Валидация форм происходит:
  1. На клиенте — для UX (мгновенная подсветка).
  2. На бэке — авторитетная проверка. Клиентская валидация не заменяет серверную.
- Серверные validation-ошибки мапятся на конкретные поля по `code` (например, `AUTH-001` → поле `email`).
- Submit-обработчик дизейблит форму на время запроса (`isSubmitting`).
- Enter в текстовом поле формы — субмитит форму (если форма не многострочная). Esc в модалках — закрывает.

## Списки и keys

- `key` — стабильный уникальный идентификатор (UUID сущности, не индекс массива).
- Никаких `key={index}` для динамических списков (только для статически фиксированных).
- Для виртуализации длинных списков (чат-история, список комнат с сотнями элементов) — выбранная в `03-decisions.md` библиотека или ручное окно.

## Условный рендер

- `&&` для bool-условий: `{isLoading && <Spinner />}`.
- Тернарник для двух вариантов: `{ok ? <A /> : <B />}`.
- Не вложенные тернарники глубже одного уровня — выноси в переменную или функцию-renderer.
- Не использовать `&&` с числами — `{count && <X />}` отрендерит `0`. Только `{count > 0 && <X />}`.

## Accessibility (a11y)

- Каждый интерактивный элемент имеет видимое название или `aria-label`.
- Кнопки — `<button type="button">` или `<button type="submit">`. Никогда `<div onClick>` — теряется keyboard и a11y.
- Формы — `<form onSubmit={...}>`, поля — `<label htmlFor>` + `<input id>`.
- Картинки — `<img alt="...">`. Декоративные — `alt=""`.
- Цветовой контраст ≥ AA по WCAG (4.5:1 для текста, 3:1 для крупного).
- Keyboard navigation:
  - Tab — переход по интерактивным элементам в логическом порядке.
  - Enter — primary action.
  - Esc — закрытие модалок / отмена.
  - Стрелки — для виджетов-меню / списков с выбором.
- Никаких `tabIndex={-1}` на видимых интерактивных элементах.
- Для кастомных виджетов (комбобокс, табы, дропдаун) — соответствующая ARIA-роль и поведение (`role="combobox"`, `aria-expanded`, `aria-controls`).
- Никаких `autoFocus` без необходимости — может ломать flow для screen reader.

## Стилизация

- Стратегия стилизации (CSS Modules / Tailwind / styled-components / ванильные CSS-файлы) — выбирается в `03-decisions.md` проекта и не микшируется.
- Имена CSS-классов (если применимо) — kebab-case.
- Никаких inline-стилей через `style={{...}}` для статической стилизации. Только для динамических вычисляемых значений (например, `transform: translateX(${offset}px)`).

## Безопасность

- НИКОГДА `dangerouslySetInnerHTML` без явной санитизации и согласования.
- Текст сообщений от пользователей рендерится как text-node (React по умолчанию экранирует). Никаких обходов.
- URL пользовательских ссылок проходят валидацию протокола: разрешены `http:` / `https:` / `mailto:`; запрещены `javascript:`, `data:`, `vbscript:`.
- `target="_blank"` обязательно с `rel="noopener noreferrer"`.

## Перерендеры

- Не оптимизировать преждевременно. `React.memo` / `useMemo` / `useCallback` — когда профайлер показывает реальную проблему.
- Селекторы Zustand — отдельные стабильные функции, чтобы не подписываться на весь store (см. `Zustand Stores.txt`).
- Тяжёлые списки — виртуализация после согласования.

## Структура файла компонента

```
features/{feature}/components/LoginForm.tsx

  ↓ порядок секций:

1. Импорты (внешние → @/shared → @/features → ./)
2. Типы и константы файла
3. Тело компонента (default export НЕ используем — named export)
4. Вспомогательные приватные функции/компоненты ниже
```

- Один файл — один основной компонент. Приватные саб-компоненты допустимы, если используются только здесь.
- Если саб-компонент переиспользуется — выносить в отдельный файл.

## Запрещено

- Классовые компоненты.
- Default exports.
- `dangerouslySetInnerHTML` без согласования.
- `<div onClick>` вместо `<button>`.
- Прямая мутация state (`state.x = y` или `array.push(...)`).
- Хуки в условиях / циклах.
- Inline-определения типов props в сигнатуре (`function X(props: { a: string }) {}`) — типы выносить выше.
- Импорт CSS-файла из другой фичи (стили фичи живут с компонентами фичи).

## Что обязан проверить агент перед коммитом

1. Все применимые состояния (loading/empty/error/success) реализованы и видны в тестах.
2. Все интерактивные элементы имеют доступное имя.
3. Keyboard navigation работает (хотя бы Tab + Enter + Esc для модалок).
4. Нет `any` в props.
5. Нет inline-функций в JSX, передающихся мемоизированным детям.
6. Все списки используют стабильный `key` (UUID, не индекс).
7. Стилизация соответствует выбранной стратегии (без mixin'а).

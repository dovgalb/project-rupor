# Tests Style — как писать тесты в проекте Rupor

Общий стиль для всех тестов проекта. Специфика доменных тестов — в `Domain model test.txt`.

## Философия

- Тесты — это документация поведения. Читаются чаще, чем пишутся.
- Тест должен падать по понятной причине. Не «assertion failed», а «InsertUser: expected err = ErrEmailTaken, got nil».
- Тест, который флакает, — хуже, чем отсутствие теста. Флаки детерминируем или удаляем.
- Один тест — одно поведение. Несколько assert-ов допустимы, если они описывают одно поведение.

## Уровни тестов

1. **Unit (domain)** — чистые тесты сущностей, без моков и I/O. См. `Domain model test.txt`.
2. **Unit (usecase)** — тесты сценариев с фейковыми реализациями интерфейсов. Без БД и HTTP.
3. **Integration (repository)** — тесты репозиториев против реального PostgreSQL в Docker.
4. **Integration (http)** — тесты хендлеров через `httptest` поверх полного стека (реальный use case, реальный или fake репозиторий).
5. **End-to-end** — опционально, если появится; через docker-compose.

Большая часть ценности — в уровнях 1 и 2. Не инвертируй пирамиду тестов.

## Общие правила для всех уровней

### Стандартная библиотека

Используем `testing` из стандартной библиотеки. Никаких testify, ginkgo, gomega, gocheck без согласования. Для сравнения сложных структур допустим `github.com/google/go-cmp/cmp`, если согласовано.

### t.Parallel()

Вызываем `t.Parallel()` в каждом тесте и подтесте, если тест не использует общий ресурс с другими. Для интеграционных тестов с общей БД — либо изолируем по схеме/базе, либо не параллелим в рамках группы.

### Table-driven там, где это уменьшает дублирование

```go
cases := []struct {
    name  string
    input X
    want  Y
}{...}

for _, tc := range cases {
    tc := tc
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        ...
    })
}
```

Если у каждого кейса своя сложная сборка — разбить на отдельные тесты. Принуждать всё в таблицу не нужно.

### Хелперы с t.Helper()

Любая функция, которая вызывает `t.Fatalf` / `t.Errorf`, должна начинаться с `t.Helper()`. Иначе ошибки будут указывать на строку внутри хелпера, а не на строку в тесте.

### Детерминизм

- Время — передаётся снаружи. Внутри тестируемого кода — интерфейс `Clock` или аргумент `now time.Time`.
- UUID / id — передаются снаружи или генерируются через инжектируемый `UUIDGenerator`.
- Рандом — инжектируется. Либо seed фиксируется.
- Нет зависимости от порядка map-итераций.
- Нет зависимости от текущего timezone.

### Сравнения

- Для ошибок — `errors.Is` (sentinel) или `errors.As` (типизированные).
- Для простых значений — явное сравнение через `!=` и `t.Fatalf`.
- Для структур с приватными полями — через геттеры.
- Для сложных публичных структур — `cmp.Diff`, если согласовано.
- Не использовать `reflect.DeepEqual` для сущностей с временем — сначала нормализуй время.

## Тесты use case-слоя

### Фейковые реализации, не моки

Для интерфейсов, от которых зависит use case, пишем фейки руками:

```go
type fakeUserRepository struct {
    byID    map[string]*domain.User
    byEmail map[string]*domain.User
    saved   []*domain.User
}

func newFakeUserRepository() *fakeUserRepository {
    return &fakeUserRepository{
        byID:    map[string]*domain.User{},
        byEmail: map[string]*domain.User{},
    }
}

func (r *fakeUserRepository) Save(ctx context.Context, u *domain.User) error {
    r.byID[u.ID().String()] = u
    r.byEmail[u.Email().String()] = u
    r.saved = append(r.saved, u)
    return nil
}
```

Это яснее, чем mockgen/gomock, и даёт полный контроль. Фейки живут рядом с тестом в `usecase/` пакете.

### Что тестируем в use case

1. Happy path: на валидном входе сценарий возвращает ожидаемый output, состояние фейков изменено правильно.
2. Ошибочные сценарии: запрошенные инварианты нарушены, use case возвращает конкретную ошибку, состояние не изменилось (или откатилось).
3. Взаимодействие с зависимостями: нужный метод репозитория вызван, с нужными аргументами.
4. Идемпотентность, если ожидается.
5. Граничные условия: пустые списки, максимальные длины, таймауты.

### Не тестируем в use case

- Бизнес-инварианты домена, которые уже покрыты в domain-тестах (избыточное покрытие).
- Форматы JSON, HTTP-коды (это транспорт).
- SQL-запросы (это репозиторий).

### Структура файла

Тест лежит рядом с кодом: `register_user.go` → `register_user_test.go`, пакет `usecase_test` (чёрный ящик).

## Интеграционные тесты репозиториев

### Реальный PostgreSQL

Репозитории тестируются против настоящей БД. Поднимается через docker-compose test-профиль или через `testcontainers-go` (по согласованию).

### Изоляция

Каждый тестовый запуск:
- Использует отдельную тестовую БД или схему.
- Применяет миграции до запуска тестов.
- Чистит данные между тестами — через `TRUNCATE` или транзакцию, откатываемую в конце теста.

### Фикстуры

- Используем builder-ы (см. `Builder.txt`) для создания доменных сущностей.
- Вставляем в БД через `repo.Save(ctx, user)`, а не прямым SQL — это проверяет маппинг заодно.
- Не загружаем тяжёлые seed-файлы, если не нужно.

### Что тестируем

1. Happy path: Save, FindByID, Update, Delete работают.
2. Маппинг: записали → прочитали → сравнили с исходной сущностью.
3. Ошибки БД → доменные ошибки: insert дубликата → `ErrEmailTaken`.
4. Транзакции: если отменили — ничего не сохранилось.
5. Пагинация, сортировка, фильтры, если есть.

## Интеграционные тесты HTTP

Используем `httptest.NewServer` поверх собранного роутера. Внутри — реальные use case, фейковые или реальные репозитории (предпочитаем реальные, если тест интеграционный).

### Что тестируем

1. HTTP-коды для каждого сценария (200, 201, 400, 401, 403, 404, 409, 500).
2. Формат тела ответа (структура JSON).
3. Валидация запроса.
4. Авторизация: без токена — 401, с невалидным — 401, без прав — 403.
5. End-to-end: POST создаёт, GET возвращает, DELETE удаляет.

### Чего не тестируем

- Глубокие бизнес-правила (уже покрыты юнитами).
- Все ветки валидации (основные — да, мелочи — нет).

## Нейминг тестов

- `TestFunction_Scenario` или `TestType_Method_Scenario`.
- Имена подтестов — на русском или английском, единообразно в рамках файла.
- Что описывает имя: СЦЕНАРИЙ, а не реализацию. «возвращает ошибку при пустом email», а не «проверяет что если пусто то err».

## Структура одного теста

Arrange / Act / Assert — явно разделяем пустой строкой:

```go
func TestRegisterUser_Success(t *testing.T) {
    t.Parallel()

    // Arrange
    repo := newFakeUserRepository()
    hasher := newFakeHasher()
    now := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
    uc := usecase.NewRegisterUser(repo, hasher, fixedClock(now))

    // Act
    out, err := uc.Execute(ctx, usecase.RegisterUserInput{
        Email:    "user@example.com",
        Username: "tester",
        Password: "sup3rs3cret",
    })

    // Assert
    if err != nil {
        t.Fatalf("Execute: %v", err)
    }
    if len(repo.saved) != 1 {
        t.Fatalf("saved users = %d, want 1", len(repo.saved))
    }
    if out.UserID == "" {
        t.Fatal("expected non-empty user id")
    }
}
```

## Что запрещено

- `time.Sleep` в тестах без крайней необходимости. Вместо этого — каналы, условные переменные, poll с таймаутом.
- Тесты, зависящие от сети, если тест не помечен как сетевой.
- Тесты, зависящие от текущей даты.
- Тесты, читающие из глобальных переменных окружения без явного `t.Setenv`.
- Общий state между тестами через глобальные переменные.
- Копипаст длинных setup-блоков — выносить в хелперы.

## Красные флаги

- Тест проходит сегодня и падает завтра → где-то использовали `time.Now()`.
- Тест проходит локально и падает в CI → зависимость от порядка, от таймзоны, от параллельности.
- Тест проверяет внутренние детали реализации (приватные поля, вызов конкретного SQL) → переписать на проверку поведения.
- Тест требует 20 строк моков для одного сценария → use case слишком большой, разбить.
- Падающий тест «починили» добавлением `time.Sleep` → найди настоящую причину.

## Что обязан сделать агент перед PR

1. `go test ./...` проходит.
2. `go test -race ./...` проходит (race detector).
3. Новые тесты добавлены ко всем новым веткам кода (позитивным и негативным).
4. Тесты детерминированы — запусти несколько раз, убедись в стабильности.
5. Нет закомментированных или `t.Skip(...)` без обоснования.

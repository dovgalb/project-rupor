# Go Style — как писать код на Go в проекте Rupor

База — `Effective Go` и `Google Go Style Guide`. Ниже — наши уточнения и правила, обязательные для агентов Claude.

## Общее

- Go 1.22+.
- `gofmt` / `goimports` — обязательно. Любой код, не проходящий `gofmt`, считается сломанным.
- `golangci-lint` — обязательный линтер, запуск через `make lint`.
- Плоское лучше вложенного. Скучное лучше креативного. Явное лучше неявного.
- Код и коммиты — по-английски. Комментарии и сообщения пользователю — по-русски.

## Именование

- Пакеты: короткие, в нижнем регистре, без подчёркиваний и camelCase. `auth`, `room`, `channel`. Никаких `utils`, `common`, `helpers`, `models`.
- Переменные: короткие в узком scope (`i`, `u`, `err`), длиннее — в широком (`userRepository`, `currentUser`).
- Экспортируемые идентификаторы — с большой буквы, неэкспортируемые — с маленькой.
- Интерфейсы: имя по роли, не по реализации. `UserRepository`, `PasswordHasher`, `Clock`. Не `IUserRepository`, не `UserRepositoryInterface`.
- Ошибки: `ErrXxx` для sentinel-ошибок, `XxxError` для типизированных.
- Тесты: `TestFunc`, `TestType_Method`.
- Константы: обычный CamelCase, без `SCREAMING_SNAKE_CASE`.

## Пакеты

- Один пакет — одна чёткая ответственность.
- Имя пакета отражает то, что пакет ПРЕДОСТАВЛЯЕТ, а не то, что он СОДЕРЖИТ. `auth`, не `authstuff`.
- Не создавать пакеты ради одной функции. Сначала помещаем код в существующий пакет, выносим когда накопится.
- Не делать циклических импортов (Go их не даст, но архитектурно их тоже быть не должно — см. Architecture Layers).

## Структуры и конструкторы

- Поля структуры — приватные по умолчанию, публичные только когда нужно.
- Конструктор `NewXxx` возвращает `(*Xxx, error)`, если может зафейлиться, иначе `*Xxx`.
- Zero value — делать полезным, если это возможно и дёшево. Если zero value невалиден — скрывать структуру за конструктором.
- Не делать `Init()` методов. Вся инициализация — в конструкторе.

## Ошибки

- Возвращать ошибку — последним значением из функции.
- Оборачивать через `fmt.Errorf("context: %w", err)`, а не `errors.Wrap`.
- Сравнивать через `errors.Is` для sentinel, `errors.As` для типизированных.
- Не игнорировать ошибки. `_ = x.Close()` допустимо только для `defer Close()` на read-only ресурсах, и то лучше логировать.
- Не логировать и одновременно возвращать ошибку — выбирай одно (обычно: логирует тот, кто принимает решение что делать).
- `panic` — запрещён в продовом коде, допустим только в composition root при невозможности стартовать и в тестах.

## Контекст

- `context.Context` — первым параметром, если функция может блокироваться, делает I/O или может быть отменена.
- Не класть `context.Context` в структуры (за редчайшими исключениями).
- Не передавать `context.Background()` глубже точки входа. Пробрасывать контекст запроса до самого низа.
- Не использовать `context.Value` для бизнес-данных. Только для cross-cutting: request-id, trace, auth-principal.

## Управление потоком

- Ранние возвраты (early return). Не `else` после `return`.
- Не вложенные `if` более 3 уровней. Если глубже — выносить в функцию.
- `switch` предпочтительнее длинных `if/else if`.
- `for range` предпочтительнее индексных циклов, если индекс не нужен.

## Горутины и каналы

- Горутина должна иметь явного владельца, который знает, как её остановить.
- Никаких fire-and-forget горутин в продовом коде. Всегда — `context.Context` или явный `done` канал.
- Захват переменных цикла в горутине — `v := v` перед `go func()`. В Go 1.22 это исправлено для `for range`, но в `for i := 0` — всё ещё актуально.
- Каналы закрывает производитель, а не потребитель.
- Предпочитать `sync.WaitGroup` и `errgroup` для ожидания группы горутин.
- Мьютексы — только когда действительно нужны. Предпочитать неизменяемость или передачу через каналы.

## Интерфейсы

- Интерфейс объявляется в месте использования (потребитель), а не в месте реализации. Это главное отличие от Java/C#.
- Маленькие интерфейсы лучше больших. `io.Reader` — эталон.
- Не делать интерфейс «на всякий случай». Интерфейс появляется, когда нужна подменяемость: тесты, несколько реализаций, инверсия зависимостей между слоями.
- Не экспортировать интерфейс, если он нужен только внутри пакета.

## Комментарии и документация

- Каждая экспортируемая функция/тип — с doc-комментом, начинающимся с имени: `// NewUser creates ...`.
- Комментарии в коде — по-русски, кратко, объясняют ЗАЧЕМ, а не ЧТО. Код отвечает на «что».
- Не комментировать очевидное. `// increment counter` над `counter++` — мусор.
- TODO/FIXME — с автором и контекстом: `// TODO(bogdan): вынести после MR #123`.

## Конфигурация

- Только через переменные окружения. Никаких `config.yaml`, `config.toml`.
- Парсинг — в `config/` пакете, единая структура, валидация при старте.
- Fail fast: невалидный конфиг — не стартуем.

## Логирование

- Единая библиотека логирования (согласована: `log/slog` из стандартной библиотеки).
- Структурированные логи, не форматированные строки.
- Уровни: DEBUG (разработка), INFO (события), WARN (аномалии, но система работает), ERROR (сбой, требующий внимания).
- Не логировать PII и секреты. Пароли, токены, email по возможности маскировать.

## SQL

- Только через sqlc. Никакого ORM.
- SQL-запросы лежат в `internal/<домен>/repository/postgres/queries/`.
- sqlc генерирует типизированные методы, которые вызывает репозиторий.
- Транзакции — явно через `pgx.Tx`, оборачивая в методе репозитория.

## Горизонтальные практики

- Не использовать глобальные переменные для состояния. Только для sentinel-ошибок и констант.
- Не использовать `init()` для тяжёлых действий. `init()` только для регистрации в реестрах стандартной библиотеки, если это необходимо.
- Не прятать побочные эффекты за гетерами.
- Не делать «умную» рефлексию, если можно обойтись кодогенерацией или явным кодом.

## Запрещено без согласования

- Добавлять новые зависимости в `go.mod`.
- Менять публичное API модулей.
- Писать свой ORM, свою DI-библиотеку, свой роутер.
- Использовать `reflect` в hot path.
- Использовать `unsafe`.
- Игнорировать ошибки через `_`.

## Что обязан проверить агент перед коммитом

1. Код форматируется `gofmt`.
2. Проходит `go vet` и `golangci-lint run`.
3. Тесты проходят: `go test ./...`.
4. Нет новых импортов сторонних библиотек без согласования.
5. Нет нарушений правил слоёв (см. Architecture Layers.txt).

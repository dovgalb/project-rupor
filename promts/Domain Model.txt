# Domain Model — как строить богатые доменные модели

Этот документ описывает, как наполнять доменные сущности в `internal/<домен>/domain/`. Мы строим rich domain model, а не anemic DTO.

## Базовая идея

Доменная сущность — это НЕ набор публичных полей. Это объект, который:
- Гарантирует свои инварианты в любой момент жизни.
- Предоставляет методы, выражающие бизнес-операции.
- Не даёт клиенту привести себя в невалидное состояние.

Если сущность — это просто `struct` с публичными полями без методов, это анемичная модель. Это антипаттерн для нашего проекта.

## Что лежит в domain-пакете

1. **Сущности (Entities)** — объекты с идентичностью (`User`, `Room`, `Channel`, `Message`).
2. **Value Objects** — объекты, определяемые значением (`Email`, `Username`, `ChannelName`, `MessageContent`).
3. **Доменные ошибки** — `var ErrInvalidEmail = errors.New("invalid email")`.
4. **Доменные события** (если используются) — `UserRegistered`, `MessagePosted`.
5. **Доменные сервисы** — только когда операция не принадлежит одной сущности (например, проверка уникальности между сущностями через доменный интерфейс).

## Что НЕ лежит в domain-пакете

- Импорты из `usecase/`, `transport/`, `repository/`.
- Сторонние библиотеки (кроме стандартной библиотеки Go и `github.com/google/uuid`, если согласовано).
- JSON-теги, db-теги, теги валидации фреймворков.
- SQL, HTTP, WebSocket, любые I/O.
- Конфигурация, логирование, метрики.
- Хеширование паролей, генерация токенов — это технические детали (живут в адаптерах).

## Конструкторы с инвариантами

Любое создание сущности из «сырых» данных идёт через конструктор, который проверяет инварианты.

```go
func NewUser(id UserID, email Email, username Username, createdAt time.Time) (*User, error) {
    if id.IsZero() {
        return nil, ErrInvalidUserID
    }
    if createdAt.IsZero() {
        return nil, ErrInvalidCreatedAt
    }
    return &User{
        id:        id,
        email:     email,
        username:  username,
        createdAt: createdAt,
    }, nil
}
```

Поля — приватные. Доступ — через геттеры. Мутации — через методы, выражающие бизнес-операцию, а не через сеттеры.

## Value Objects

Value object — это небольшой иммутабельный тип, который:
- Валидирует себя в конструкторе.
- Не имеет идентичности.
- Сравнивается по значению.

```go
type Email struct {
    value string
}

func NewEmail(raw string) (Email, error) {
    raw = strings.TrimSpace(strings.ToLower(raw))
    if !emailRegex.MatchString(raw) {
        return Email{}, ErrInvalidEmail
    }
    return Email{value: raw}, nil
}

func (e Email) String() string { return e.value }
```

Использовать value objects для: email, username, пароль-хеш (как value object-обёртка), id сущностей, имена каналов, текст сообщений с ограничениями длины.

## Методы, выражающие бизнес-операции

Плохо:
```go
user.IsActive = true
user.DeactivatedAt = nil
```

Хорошо:
```go
func (u *User) Activate(now time.Time) error {
    if u.isActive {
        return ErrAlreadyActive
    }
    u.isActive = true
    u.deactivatedAt = time.Time{}
    return nil
}
```

Метод называется языком домена, а не CRUD-языком. Не `SetStatus`, а `Activate`, `Ban`, `Deactivate`. Не `SetOwner`, а `TransferOwnership`.

## Инварианты всегда истинны

Если сущность существует в памяти, её инварианты выполнены. Невозможно получить `User` с невалидным email — потому что конструктор не даст это сделать. Никакой метод не должен оставить сущность в невалидном состоянии: если операция не может быть выполнена — метод возвращает ошибку и НЕ меняет состояние.

## Что может быть в rich-модели

- Приватные поля.
- Геттеры (`Email() Email`, `CreatedAt() time.Time`).
- Конструктор `New...` для создания новой сущности.
- Конструктор восстановления из хранилища `ReconstructUser(...)` или `FromPersistence(...)` — используется репозиторием, имеет те же инварианты, но принимает уже существующий id и timestamps.
- Методы бизнес-операций.
- Методы-запросы (`CanPostIn(channel) bool`, `IsOwnerOf(room) bool`).
- Доменные события, накапливаемые в сущности (опционально).

## Что не может быть в rich-модели

- Публичные сеттеры полей.
- Публичные поля (кроме редких случаев простых value objects, где все поля read-only через неэкспортируемые).
- Методы, обращающиеся к БД, файлам, сети.
- Логирование, метрики, трассировка.
- Зависимости от репозиториев (сущность не знает, как себя сохранить).
- Флаги «грязности» (`isDirty`) или «новизны» (`isNew`) — это забота репозитория.

## Два конструктора: New vs Reconstruct

- `NewUser(...)` — для создания новой сущности в use case. Генерирует id, устанавливает createdAt = now, проверяет инварианты создания.
- `ReconstructUser(...)` — для восстановления сущности из БД в репозитории. Принимает все поля как есть, проверяет инварианты (но не «создаёт заново»). Используется только репозиториями.

Это разделение важно: `NewUser` может не принимать id (генерирует сам или получает от генератора), а `ReconstructUser` принимает всё.

## Доменные ошибки

Объявляются в `domain/errors.go`:
```go
var (
    ErrInvalidEmail      = errors.New("invalid email")
    ErrInvalidUsername   = errors.New("invalid username")
    ErrUserAlreadyActive = errors.New("user already active")
)
```

Use case и транспорт мапят их через `errors.Is`. Для ошибок с данными — типизированные ошибки:
```go
type ValidationError struct {
    Field  string
    Reason string
}

func (e ValidationError) Error() string { ... }
```

## Связи между сущностями

В rich-модели ссылки между сущностями — это id, а не вложенные объекты. `Message` содержит `AuthorID UserID`, а не `Author *User`. Загрузку связей оркестрирует use case через отдельные репозитории.

Исключение: агрегаты. Если две сущности всегда живут вместе и одна не существует без другой, можно держать их в одном агрегате. Для MVP стараемся избегать сложных агрегатов.

## Агрегаты (коротко)

Агрегат — это кластер сущностей с единым корнем, через который происходит весь доступ. Внешние клиенты работают только с корнем. Пример: `Room` как корень, `Role` внутри комнаты — только через методы `Room`.

Правила:
- Изменения внутри агрегата — атомарны.
- Один use case — один агрегат за транзакцию (по возможности).
- Ссылки между агрегатами — по id.

## Красные флаги

- В `domain/` импортируется что-то, кроме стандартной библиотеки → СТОП.
- Сущность — это просто struct с публичными полями → анемичная модель, переделать.
- Use case напрямую меняет поля сущности → метод бизнес-операции отсутствует, добавить.
- Метод сущности принимает `context.Context` → почти всегда признак того, что логика не доменная.
- Метод сущности возвращает `*sql.Tx` или принимает его → утечка инфраструктуры.

## Когда сомневаешься

Спроси себя: «Это правило было бы истинным, если бы у нас не было БД и HTTP?» Если да — это domain. Если нет — это use case или адаптер.

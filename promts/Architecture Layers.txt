# Архитектура проекта Rupor — Clean Architecture

Этот документ описывает правила слоистой архитектуры для проекта. Все агенты Claude обязаны следовать им при проектировании и написании кода.

## Принципы

- Чистая архитектура (Clean Architecture) в адаптации под Go.
- Зависимости направлены строго внутрь: внешние слои знают про внутренние, внутренние ничего не знают про внешние.
- Внутренние слои не импортируют пакеты внешних слоёв.
- Доменная логика не зависит от фреймворков, БД, HTTP, WebSocket, JSON-тегов и сторонних библиотек.
- Связь между слоями — через интерфейсы, объявленные в слое-потребителе (принцип инверсии зависимостей).
- Плоское лучше вложенного. Скучное лучше креативного. Явное лучше неявного.

## Слои (от центра наружу)

### 1. Domain (доменный слой)
Расположение: `internal/<домен>/domain/`

- Чистые сущности и value objects.
- Бизнес-правила, не зависящие ни от чего внешнего.
- Только стандартная библиотека Go. Никаких импортов из других слоёв проекта, никаких сторонних библиотек.
- Никаких JSON-тегов, тегов БД, тегов валидации фреймворков.
- Ошибки домена объявляются здесь же (`var ErrXxx = errors.New(...)`).

Что лежит:
- Структуры сущностей (`User`, `Room`, `Channel`, `Message`).
- Конструкторы с инвариантами (`NewUser(...) (*User, error)`).
- Методы сущностей, выражающие бизнес-правила.
- Доменные ошибки.

### 2. Use Cases / Application (слой сценариев)
Расположение: `internal/<домен>/usecase/` (или `service/`, если выбран этот термин — придерживаться одного во всём проекте).

- Реализует прикладные сценарии: «зарегистрировать пользователя», «отправить сообщение», «создать комнату».
- Оркеструет вызовы доменных сущностей и репозиториев.
- Объявляет интерфейсы того, что ему нужно от внешнего мира (репозитории, хешеры паролей, генераторы токенов, часы, UUID, шина событий).
- Не знает про HTTP, WebSocket, SQL, JSON.
- Возвращает доменные ошибки или обёрнутые ошибки уровня приложения.

Что лежит:
- Структуры use case'ов (`type RegisterUser struct { repo UserRepository; hasher PasswordHasher; ... }`).
- Методы-сценарии (`Execute(ctx, input) (output, error)`).
- Интерфейсы зависимостей (`UserRepository`, `PasswordHasher`, `TokenIssuer` и т.п.).
- DTO входа/выхода use case'ов (без транспортных тегов).

### 3. Interface Adapters (адаптеры)
Расположение:
- HTTP-обработчики: `internal/<домен>/transport/http/`
- WebSocket-обработчики: `internal/<домен>/transport/ws/`
- Реализации репозиториев: `internal/<домен>/repository/postgres/`
- Маперы между слоями: рядом с адаптером.

- Преобразуют данные из внешнего формата (HTTP-запрос, SQL-строка, WS-сообщение) в DTO use case'а и обратно.
- Реализуют интерфейсы, объявленные в use case-слое.
- Здесь живут JSON-теги, теги sqlc, валидация входных DTO.
- HTTP-хендлер: распарсить запрос → вызвать use case → сериализовать ответ → отдать HTTP-код.
- Репозиторий: транслирует доменные структуры в SQL и обратно. SQL — через sqlc.
- Никакой бизнес-логики в адаптерах. Хендлер не принимает решений по правилам — он только транслирует.

### 4. Infrastructure / Frameworks & Drivers (внешний слой)
Расположение: `cmd/server/`, `pkg/`, `config/`, `migrations/`.

- Точка входа `cmd/server/main.go`: чтение конфигурации, создание подключений, сборка зависимостей (composition root), запуск сервера.
- Драйверы: пул PostgreSQL, WebSocket-хаб, HTTP-роутер chi, миграции.
- Никакой бизнес-логики и доменных правил. Только инициализация и склейка.

## Правила импорта (обязательно к проверке)

- `domain/` импортирует ТОЛЬКО стандартную библиотеку.
- `usecase/` импортирует ТОЛЬКО `domain/` и стандартную библиотеку.
- `transport/...` и `repository/...` импортируют `usecase/` и `domain/`, но НЕ наоборот.
- `cmd/server/` импортирует всё необходимое для сборки графа зависимостей.
- Запрещено: `domain/` импортирует `usecase/`. Запрещено: `usecase/` импортирует `transport/` или `repository/`. Запрещено: одна доменная папка импортирует `transport/` или `repository/` другой доменной папки.

## Поток данных (на примере регистрации пользователя)

1. HTTP-запрос приходит в `internal/auth/transport/http/register_handler.go`.
2. Хендлер парсит JSON в транспортный DTO, валидирует формат.
3. Хендлер маппит DTO в input use case'а и вызывает `RegisterUser.Execute(ctx, input)`.
4. Use case создаёт доменную сущность через `domain.NewUser(...)`, которая проверяет бизнес-инварианты.
5. Use case вызывает `UserRepository.Save(ctx, user)` (интерфейс объявлен в `usecase/`).
6. Реализация репозитория в `internal/auth/repository/postgres/` транслирует доменную сущность в SQL через sqlc.
7. Use case возвращает output, хендлер сериализует его в JSON и отдаёт ответ.

## Тестируемость

- Доменный слой тестируется юнит-тестами без моков.
- Use case'ы тестируются юнит-тестами с фейковыми реализациями интерфейсов (написанными вручную, без mock-генераторов).
- Адаптеры тестируются интеграционно: HTTP — через `httptest`, репозитории — против реальной PostgreSQL в Docker.
- Все функции должны быть тестируемыми. Предпочитать чистые функции.

## Ошибки

- Доменные ошибки объявляются в `domain/` через `errors.New` или типизированные ошибки.
- Use case оборачивает технические ошибки (`fmt.Errorf("save user: %w", err)`).
- Адаптер транспорта мапит ошибку в HTTP-код в одном месте (`errors.Is` / `errors.As`).
- Никаких `panic` в продовом коде, кроме composition root при невозможности стартовать.

## Что НЕЛЬЗЯ делать

- Класть SQL в use case или domain.
- Класть HTTP-логику (статусы, заголовки, JSON) в use case или domain.
- Передавать `*http.Request` или `http.ResponseWriter` глубже хендлера.
- Использовать глобальные переменные для зависимостей. Только явное внедрение через конструкторы.
- Делать «тонкие» сервисы, которые просто проксируют вызов в репозиторий — это значит, что use case не нужен или модель неправильно спроектирована. Обсудить с пользователем.
- Создавать пакеты `utils`, `helpers`, `common`, `models` без конкретной ответственности.
- Использовать ORM. Только sqlc.
- Добавлять новые библиотеки без явного согласования с пользователем.

## Что обязан делать агент перед написанием кода

1. Определить, к какому слою относится изменение.
2. Проверить, что предлагаемые импорты не нарушают правила направления зависимостей.
3. Если требуется новая зависимость use case'а — объявить интерфейс в use case-слое, а реализацию — в адаптере.
4. Если бизнес-правило — оно идёт в `domain/`, а не в `usecase/` и не в хендлере.
5. Если возникает соблазн нарушить слой — остановиться и спросить пользователя.

## Терминология (фиксируем один вариант)

- Слой сценариев называем `usecase` (не `service`), папка — `usecase/`.
- Интерфейсы зависимостей именуем по роли: `UserRepository`, `PasswordHasher`, `TokenIssuer`, `Clock`, `UUIDGenerator`.
- DTO use case'ов: `RegisterUserInput`, `RegisterUserOutput`.
- Транспортные DTO: `RegisterUserRequest`, `RegisterUserResponse`.

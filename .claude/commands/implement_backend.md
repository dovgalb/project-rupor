## Фаза 1: Создать команду агентов

### 1.1 TeamCreate

Используй инструмент **TeamCreate**:

- `team_name` — производный от имени фичи, например `{feature-slug}-impl`
- `description` — `"Реализация {имя фичи} — Go бэкенд"`

Создаёт:

- Конфиг команды: `~/.claude/teams/{team-name}/config.json`
- Общий список задач: `~/.claude/tasks/{team-name}/`

### 1.2 Создать задачи

Используй **TaskCreate** для каждой фазы реализации из плана.

Для каждой фазы создать задачу:

- `subject`: `"Фаза N: {Название}"`
- `description`: вставить ПОЛНОЕ описание фазы из плана — файлы для создания/изменения, ключевые решения, критерии верификации. Задача должна быть **самодостаточной** — исполнитель читает ТОЛЬКО её описание.
- `activeForm`: `"Реализация Фазы N: {Название}"`

После создания всех задач задать зависимости через **TaskUpdate**:

- `addBlockedBy` — связать каждую задачу с фазами, от которых она зависит (например, Фаза 2 заблокирована Фазой 1)

Создать ОДНУ дополнительную задачу в конце:

- `subject`: `"Финальный кросс-фазный ревью"`
- `description`: `"Проверить все фазы вместе на сквозные проблемы: уникальные коды ошибок, отсутствие осиротевшего кода, согласованность именования, корректность DI-цепочки, Value Objects везде"`
- `activeForm`: `"Финальный кросс-фазный ревью"`
- `addBlockedBy`: ID всех задач реализации фаз

### 1.3 Включить Delegate Mode

Войди в **Delegate Mode** (Shift+Tab). В этом режиме доступны только координационные инструменты — спавн, сообщения, управление задачами. Ты НЕ МОЖЕШЬ писать код. Это удерживает тебя в роли оркестратора.

```
## Критичные правила проекта Rupor
- **Все поля сущностей — Value Objects** — никаких голых int/string/bool
- **БЕЗ version int64** — оптимистичная блокировка через `updatedAt`-фильтрацию, не через счётчик
- **Порядок билдера**: checkRequired → fillDefault → validateBusiness
- **Restore() factory** — ВСЕ сущности используют `Restore()` для восстановления из persistence, не Builder
- **Time**: всегда `*time.Time` из `domain-common/primitives/time`, никогда stdlib time.Time
- **Int-поля**: оборачивай в VO (паттерны HintCount, RetryCount, AttemptNumber)
- **UserID из auth**: `ctx.Value("userID").(string)` через middleware, НЕ из заголовка `X-User-ID`
- **SQL только через sqlc**, никаких ORM, никакой ручной конкатенации SQL
- **Auth middleware**: применяется через chi-роутер, защищает все приватные эндпоинты
- **Конфигурация**: только через env, не через файлы

## Workflow на каждую задачу
1. TaskUpdate — статус `in_progress`
2. Прочитать ВСЕ файлы из задачи ЦЕЛИКОМ (без limit/offset)
3. Перечитать релевантные стандарты из `/prompts/` для слоя, который трогаешь
4. Подумать: кто это вызывает? Что вызывает это? Что может сломаться?
5. Реализовать
6. Self-check (ВСЕ три должны пройти до отчёта):
   go build ./internal/{домен}/...
   go test ./internal/{домен}/... -v -count=1
   golangci-lint run ./internal/{домен}/...
7. SendMessage Lead-у: "Фаза N готова. Build [V] Tests [V N passing] Lint [V]"
8. Ждать вердикта ревьюеров через Lead-а
9. Если REJECTED — починить замечания, перепрогнать self-check, переотчитаться
10. TaskUpdate `completed` ТОЛЬКО после подтверждения от Lead-а
11. Проверить TaskList — следующая незаблокированная неназначенная задача
```

### 1.5 Протокол ревью

**Отправить 4 сообщения параллельно:**

```
SendMessage to "rv-build": "Ревью Фазы N. Domain: internal/{домен}/"
SendMessage to "rv-arch":  "Ревью Фазы N. Изменённые файлы: [list]. Domain: internal/{домен}/"
SendMessage to "rv-sec":   "Ревью Фазы N. Изменённые файлы: [list]. Domain: internal/{домен}/"
```

## Фаза 3: Финальный ревью

После завершения всех phase-задач (проверить через **TaskList**) запустить **Final Cross-Phase Review** — отправить сообщения всем 4 персистентным ревьюерам параллельно (так же как в §1.5, но со cross-phase скоупом):

- **Build+Test+Lint** — полный билд/тесты/линт всего домена
- **Architecture+Standards** — прочитать ВСЕ новые файлы по ВСЕМ фазам, проверить кросс-фазную согласованность: уникальные коды ошибок, отсутствие осиротевшего кода, согласованность именования, корректность DI-цепочки в `cmd/server/`, все VO
- **Security** — прочитать ВСЕ новые файлы по ВСЕМ фазам, полный security-аудит
- **Completeness** — прочитать ПОЛНЫЙ план README.md (все фазы), проверить, что ВСЕ фазы реализованы, ВСЕ критерии приёмки выполнены, ВСЕ success-критерии из плана отмечены

**Дополнительные кросс-фазные проверки для агента Architecture+Standards:**

```
- [ ] Коды ошибок уникальны во всём модуле (не только в этой фазе)
- [ ] Нет осиротевшего кода от ранних итераций
- [ ] Нет TODO/FIXME
- [ ] Нейминг согласован по всем новым файлам
- [ ] Все поля сущностей имеют round-trip repo-тесты
- [ ] Нет циклических зависимостей между новыми пакетами
- [ ] DI-цепочка корректна в `cmd/server/` (порядок инициализации совпадает с зависимостями)
- [ ] Все Value Objects — голых типов не утекает
- [ ] Миграции в `migrations/` совпадают с repo-моделями
```

Пометить final-review задачу `completed` после прохождения всех 4 агентов.

## Фаза 4: Smoke Test

После прохождения cross-phase ревью **SendMessage** implementer-у — запустить smoke-тесты:

### 4.1 Запустить сервис

```bash
make run &
sleep 3
```

Если сервис требует зависимости (PostgreSQL), проверить, что docker-compose поднят:

```bash
make dc-up
```

### 4.2 Тестировать API эндпоинты

Для каждого нового/изменённого эндпоинта из плана прогнать curl-запросы:

```bash
curl -s http://localhost:8080/api/v1/health | jq .
curl -s -X POST http://localhost:8080/api/v1/{path} \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {test-token}" \
  -d '{"field": "value"}' | jq .
```

### 4.3 Проверить ответы

- HTTP-статус корректный (200, 201, 400, 401, 404 и т.д.)
- Тело ответа соответствует ожидаемой схеме
- Ошибки содержат типизированные коды (не голые stack traces)
- Защищённые эндпоинты возвращают 401 без токена
- Бизнес-правила соблюдаются (валидация, переходы состояний)

### 4.4 Проверить логи

Убедиться, что нет panic, нет неожиданных ошибок в логах сервиса.

### 4.5 Cleanup

```bash
kill %1
make dc-down  # если поднимался
```

### 4.6 Отчёт

Implementer отправляет результаты smoke-тестов через SendMessage Lead-у:

```
## Smoke Test Results

### Endpoints Tested
| Method | Path | Status | Expected | Actual | V/X |
|--------|------|--------|----------|--------|-----|

### Auth
- V Защищённые эндпоинты возвращают 401 без токена

### Logs
- V Нет panic
- V Структурированное логирование корректно
```

Если хоть один smoke-тест падает → fix → re-run. НЕ продолжать с упавшими smoke-тестами.

```
SendMessage:
```

НЕ вызывать TeamDelete пока активны тиммейты — упадёт.

## Фаза 7: Commit

**ВАЖНО (TEAM GIT POLICY):** Claude НЕ выполняет git-команды. Ты только **генерируешь текст коммит-сообщения**, пользователь сам делает git add / git commit.

После прохождения всех ревью (quality gates + cross-phase + smoke test) и shutdown команды, **сгенерировать предложение коммита** для пользователя.

### Правила коммит-сообщения

- **Conventional Commits** формат: `feat:`, `fix:`, `refactor:`, `test:`, `chore:`
- **НИКОГДА не добавлять `Co-Authored-By` строки** — это СТРОГО запрещено политикой проекта. Никаких упоминаний авторства, никаких `Signed-off-by`. Только описание и summary.
- **Scope** в скобках для модуля: `feat(room): add invite endpoint`
- **БЕЗ push** — пользователь сам решает, когда пушить

### Что отдать пользователю

```
Предложение коммита:

  Файлы для git add:
  - internal/{домен}/domain/{file}.go
  - internal/{домен}/usecase/{file}.go
  - migrations/{NNNN}_{name}.sql

  Сообщение:
  ----
  feat({модуль}): {краткое описание}

  - {Phase 1 summary}
  - {Phase 2 summary}
  - {Phase N summary}

  Quality: {N} phases, {N} tests, 0 lint issues
  Smoke: {N} endpoints verified
  ----
```

### Выбор типа коммита

| Type     | Когда                                  |
|----------|----------------------------------------|
| feat     | Новая фича или возможность             |
| fix      | Исправление бага                       |
| refactor | Реструктуризация без изменения поведения |
| test     | Только добавление/изменение тестов     |
| chore    | Поддержка, миграции, конфиги           |

## Правила

1. **Lead НИКОГДА не пишет код** — координирует, назначает, агрегирует, решает (Delegate Mode это обеспечивает)
2. **Никакой фазы без одобрения** — все 4 review-агента должны пройти, никаких шорткатов
3. **Стандарты — это закон** — нарушения `/prompts/` = REJECT
4. **Только полное чтение файлов** — частичное чтение = частичное понимание = баги
5. **Стоп при несоответствиях** — спросить пользователя, не импровизировать
6. **Логировать отказы** — паттерны в отказах = стандарты нуждаются в обновлении
7. **Value Objects везде** — голые типы в сущностях = автоматический REJECT
8. **API команд агентов** — TeamCreate, TaskCreate/Update/List, SendMessage, TeamDelete
9. **Shutdown перед cleanup** — всегда корректно останавливать тиммейтов перед TeamDelete
10. **4 персистентных review-агента** — rv-build, rv-arch, rv-sec, rv-plan — заспавнены один раз, переиспользуются через SendMessage в каждом раунде ревью
11. **Completeness обязательна** — каждое ревью ДОЛЖНО проверять покрытие плана и соответствие design-у, не только качество кода
12. **План — это закон** — реализация должна точно соответствовать плану. Уменьшение области = REJECT. Допустимы только улучшения, ДОБАВЛЯЮЩИЕ к плану.
13. **GIT POLICY** — Claude НЕ запускает git. Только генерирует текст коммит-сообщения. Никаких `Co-Authored-By`.
14. **Русский язык** — все промпты, отчёты, коммит-сообщения, manual QA — на русском.

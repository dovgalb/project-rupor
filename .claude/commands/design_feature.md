# Проектирование фичи — C4 + DFD + Sequence → План кода

Ты — опытный программный архитектор, проектирующий фичу по модели C4 с обязательным согласованием с человеком на каждом этапе (human-in-the-loop).

**Базовый принцип:** сначала проектируем ЧТО и ЗАЧЕМ, потом — КАК. Никакого планирования кода до тех пор, пока архитектура не утверждена.

---

## Этап 0: Понять задачу

### 0.1 Разбор аргументов

- `$ARGUMENTS[0]` — имя фичи (slug, используется как имя директории)
- `$ARGUMENTS[1]` — путь к сервису (например, `microservices/name` или `front`)
- `$ARGUMENTS[2+]` — описание фичи, требования или ссылка на тикет (всё, что после пути к сервису)

Если аргументы отсутствуют, спросить:
```
Пожалуйста, укажи:
1. Имя фичи (slug, например "rag-strategy")
2. Путь к сервису (например, "microservices/name" или "front")
3. Описание фичи или ссылку на тикет
```

Если переданы только имя фичи и путь к сервису (без описания) — попросить пользователя описать фичу, прежде чем продолжать.

### 0.2 Прочитать запрос на фичу

- Прочитать описание фичи / тикет, переданный пользователем
- Понять **бизнес-цель** — какую проблему это решает?
- Определить критерии приёмки
- Определить, затрагивает ли фича бэкенд, фронтенд или инфраструктуру

### 0.3 Прочитать стандарты проекта и изучить структуру кодовой базы

Прочитать ВСЕ стандарты проекта:
- **Бэкенд (Go):** прочитать ВСЕ файлы в `/promts/` — Architecture Layers, Clean Architecture, Domain Model, Builder, RepoModel, Go Style, Tests Style, Domain model test

### 0.4 Решить, нужен ли ресерч

Ресерч нужен, когда:
- Ты не знаешь текущую архитектуру затрагиваемых модулей
- Фича затрагивает незнакомые части кодовой базы
- Существуют реализации, которые могут быть переиспользованы
- Точки интеграции неясны

### 0.5 Определить контекст фичи

Проанализировать фичу и решить, какие **условные документы** понадобятся (см. этап 2.3):

| Условие | Условный документ |
|---------|-------------------|
| Фича содержит доменные события | `05-events.md` |
| Бэкенд-фича с сущностями | `06-repo-model.md` |
| Бэкенд-фича | `07-standards.md` |
| Фича выставляет REST-эндпоинты | `08-api-contract.md` |
| Фича затрагивает фронтенд (`web/`) | `09-frontend.md` |
| Фича требует миграций БД | `10-migrations.md` |
| Фича использует WebSocket / WebRTC | `11-realtime.md` |

### 0.6 Проверить наличие ресерча

Если пользователь передал путь к файлу из `.thoughts/research/` — прочитать его ЦЕЛИКОМ и использовать как базу знаний.

Если ресерч нужен (см. 0.4), но не передан — остановиться и попросить пользователя:
```
Для проектирования этой фичи нужен ресерч по следующим областям:
- [область 1]
- [область 2]

Запусти: /research_codebase <вопрос>
Затем передай путь к результату: /design_feature <имя> <сервис> .thoughts/research/<файл>.md
```

НЕ запускать ресерч самостоятельно в рамках этой команды — это отдельный процесс.

## Этап 2: Проектирование (C4 + DFD + Sequence)

Создать директорию: `.thoughts/design/<feature-name>/`

Все документы — в markdown, на русском языке. В каждом документе — ссылки `файл:строка` на существующий код, если он упоминается.

### 2.1 Обязательные документы

#### `01-context.md` — C4 Level 1: System Context
- Какие внешние акторы участвуют (пользователь, внешние системы)
- Какие существующие системы затронуты (PostgreSQL, Redis, WebSocket hub, фронт)
- Границы фичи: что ВНУТРИ, что СНАРУЖИ
- Диаграмма в Mermaid (`graph TD` или `C4Context`)

#### `02-containers.md` — C4 Level 2: Containers
- Какие контейнеры проекта затронуты: `cmd/server`, `internal/<domain>`, `web/`, `migrations/`, `pkg/websocket`
- Какие НОВЫЕ контейнеры/пакеты добавляются (если вообще)
- Направления зависимостей между контейнерами
- Соответствие правилам из `promts/Architecture Layers.txt` (проверить явно)
- Диаграмма в Mermaid

#### `03-components.md` — C4 Level 3: Components
Для каждого затронутого домена в `internal/<domain>/` расписать по слоям Clean Architecture:

- **domain/** — новые сущности, value objects, доменные ошибки, доменные события
- **usecase/** — новые сценарии и интерфейсы зависимостей (порты)
- **transport/http/** — новые HTTP-хендлеры, DTO запросов/ответов
- **repository/postgres/** — новые репозитории, sqlc-запросы

Для каждого компонента:
- Имя и расположение (путь)
- Ответственность (1-2 предложения)
- Входы / выходы
- Зависимости (интерфейсы, а не реализации)
- Ссылки на существующие компоненты, если переиспользуются (`файл:строка`)

Соответствие: `promts/Clean architecture.txt`, `promts/Architecture Layers.txt`, `promts/Domain Model.txt`, `promts/Builder.txt`.

#### `04-sequence-dfd.md` — Sequence + DFD
- **Sequence diagram** (Mermaid `sequenceDiagram`) для каждого ключевого сценария: клиент → transport → usecase → repository → БД и обратно
- **Data Flow Diagram**: как данные текут через систему, где валидируются, где трансформируются
- Обработка ошибок: какие доменные ошибки возникают, как мапятся в HTTP-коды

### 2.2 Условные документы (создавать ТОЛЬКО если применимо, см. 0.5)

#### `05-events.md` — Доменные события
- Список событий, их payload, кто публикует, кто подписан
- Если события идут через WebSocket hub (`pkg/websocket`) — описать топики/каналы

#### `06-repo-model.md` — Модель репозитория и SQL
- Новые таблицы / изменения существующих (DDL)
- sqlc-запросы (сигнатуры, без реализации)
- Индексы и их обоснование
- Соответствие `promts/RepoModel.txt`

#### `07-standards.md` — Специфичные стандарты
- Явные ссылки на пункты из `promts/Go style.txt`, `promts/Tests Style.txt`, `promts/Domain model test.txt`, применимые к этой фиче
- Только если есть нетривиальные места, где стандарты особенно важны

#### `08-api-contract.md` — REST-контракт
- Эндпоинты: метод, путь (`/api/v1/...`), заголовки, тело запроса, тело ответа, коды ошибок
- Авторизация (JWT) — кто имеет доступ
- Примеры запросов/ответов (JSON)

#### `09-frontend.md` — Фронтенд (`web/`)
- Новые экраны / компоненты (React)
- Состояние (Zustand store)
- API-клиент: какие ручки дергает
- WebSocket-подписки, если есть

#### `10-migrations.md` — Миграции БД
- Имена файлов миграций (`migrations/NNNN_<name>.up.sql` / `.down.sql`)
- Порядок применения
- Обратимость (что делает down)

#### `11-realtime.md` — WebSocket / WebRTC
- Какие события летят через WS, формат payload
- Для WebRTC — какие SDP/ICE-сообщения проходят через сигнальный сервер (`internal/voice`)

### 2.3 Индексный файл `README.md`

В `.thoughts/design/<feature-name>/README.md` — оглавление всех созданных документов с кратким описанием каждого и YAML-метаданными:

```yaml
---
feature: <имя>
service: <путь>
date: YYYY-MM-DD
author: Claude
status: draft
research: <путь к ресерчу или null>
---
```

## Этап 3: Архитектурное ревью (human-in-the-loop #2)

После создания всех документов — остановиться и показать пользователю:

```
Спроектировано. Документы:
- .thoughts/design/<feature>/01-context.md
- .thoughts/design/<feature>/02-containers.md
- .thoughts/design/<feature>/03-components.md
- .thoughts/design/<feature>/04-sequence-dfd.md
- <условные документы>

Ключевые архитектурные решения:
1. <решение 1 — почему именно так>
2. <решение 2>
3. <решение 3>

Риски и компромиссы:
- <риск 1>
- <риск 2>

Альтернативы, которые я рассмотрел и отверг:
- <альтернатива 1> — причина отказа
```

Спросить: **"Готов ревьюить. Что меняем? Что утверждаем?"**

Ждать явного ответа. Возможные исходы:
- **Утверждено** → переход к этапу 4
- **Правки** → внести правки в документы, снова показать ключевые изменения, снова ждать
- **Пересмотр подхода** → вернуться к этапу 2 (возможно, к 0.4 если нужен доп. ресерч)

НЕ переходить к плану кода без явного утверждения.

## Этап 4: План реализации

Только после утверждения архитектуры. Создать `.thoughts/design/<feature-name>/plan.md`.

Разбить реализацию на 4 этапа. Каждый этап — самостоятельный, тестируемый, мержабельный.

### Шаблон плана

```markdown
---
feature: <имя>
date: YYYY-MM-DD
status: approved
---

# План реализации: <фича>

## Этап 1: Домен и миграции
**Цель:** подготовить фундамент без внешних точек входа.

- [ ] Миграции БД (`migrations/NNNN_*.sql`) — если нужны
- [ ] Доменные сущности (`internal/<domain>/domain/`)
- [ ] Value objects и доменные ошибки
- [ ] Доменные события (если есть)
- [ ] Unit-тесты домена (см. `promts/Domain model test.txt`)

**Критерий готовности:** `make test` зелёный, домен полностью покрыт тестами.

## Этап 2: Usecase и репозитории
**Цель:** бизнес-логика и доступ к данным.

- [ ] sqlc-запросы (`internal/<domain>/repository/postgres/queries/`)
- [ ] Реализация репозиториев
- [ ] Интерфейсы портов (`internal/<domain>/usecase/`)
- [ ] Сценарии (usecase)
- [ ] Unit-тесты usecase с моками репозиториев
- [ ] Интеграционные тесты репозиториев (реальный PostgreSQL)

**Критерий готовности:** сценарии работают end-to-end без HTTP-слоя, покрыты тестами.

## Этап 3: Transport (HTTP / WebSocket)
**Цель:** внешние точки входа.

- [ ] DTO запросов/ответов
- [ ] HTTP-хендлеры (`internal/<domain>/transport/http/`)
- [ ] Маппинг доменных ошибок → HTTP-коды
- [ ] Регистрация маршрутов в роутере (`cmd/server/`)
- [ ] WebSocket-обработчики (если есть)
- [ ] Тесты транспортного слоя

**Критерий готовности:** эндпоинты отвечают, контракт из `08-api-contract.md` соблюдён.

## Этап 4: Фронтенд и интеграция
**Цель:** сквозной сценарий работает в браузере.

- [ ] API-клиент (`web/src/api/`)
- [ ] Zustand store
- [ ] React-компоненты и экраны
- [ ] WebSocket-подписки (если есть)
- [ ] Ручная проверка полного сценария
- [ ] Обновление README/документации, если нужно

**Критерий готовности:** пользователь может пройти сценарий от UI до БД и обратно.

## Точки проверки с человеком

После каждого этапа — остановиться и показать:
- Что сделано
- Какие тесты зелёные
- Есть ли отклонения от проектирования
- Готово ли к мержу

НЕ переходить к следующему этапу без подтверждения.

## Ссылки

- Проектирование: `.thoughts/design/<feature>/`
- Ресерч: <путь или "не требуется">
- Стандарты: `promts/`
```

### 4.1 Адаптация плана

- Если фича **чисто backend** — этап 4 превращается в «контрактные/e2e-тесты» вместо фронта
- Если фича **чисто frontend** — этапы 1-3 сжимаются/исчезают, акцент на этапе 4
- Если фича **без миграций** — убрать соответствующий пункт из этапа 1
- Если фича **без новых доменных сущностей** (например, только новый REST-эндпоинт поверх существующих usecase) — этап 1 сводится к ревизии существующего домена

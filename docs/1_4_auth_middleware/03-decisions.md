# 03 — Decisions (Decision View)

## Решения

| # | Решение | Выбор | Рассмотренные альтернативы | Обоснование (ссылки `файл:строка`) |
|---|---------|-------|----------------------------|------------------------------------|
| ADR-001 | Не подключать сторонние middleware-библиотеки | Свои реализации Recover / Logger / CORS / RequestID / RequireAuth, без новых зависимостей в `go.mod` | (a) `github.com/go-chi/chi/v5/middleware` (RequestID/Recoverer/Logger из chi); (b) `github.com/go-chi/cors`; (c) `github.com/rs/cors` | (1) Согласовано с пользователем (вопрос UI). (2) `prompts/Go style.txt:111-117` запрещает новые зависимости без согласования. (3) Каждая middleware — 30–60 строк, типовая реализация без специфики, не оправдывает зависимость. (4) `chi/middleware.RequestID` использует свой формат `req-...` вместо UUID — нам нужен UUID для коррелятора с логами. (5) `chi/middleware.Recoverer` пишет 500 plain-text, не JSON-envelope; пришлось бы оборачивать. (6) `chi/middleware.Logger` использует ColorWriter/text — нам нужен structured slog. (7) `go-chi/cors` тянет 200+ строк ради простого whitelist + preflight, который у нас укладывается в ~60 строк. |
| ADR-002 | Порядок глобальной middleware-цепочки | `RequestID → Recover → Logger → CORS` | (a) `Logger → RequestID` (логгер не видит request_id); (b) `Recover → RequestID` (если recover паникует, request_id не установлен); (c) `CORS → RequestID → ...` (CORS не получает request_id в логах preflight) | (1) `RequestID` первый, потому что все нижестоящие должны логировать `request_id`, в т. ч. Recover при panic и Logger в access-log (`02-behavior.md`, DFD-1). (2) `Recover` стоит ВЫШЕ `Logger`, чтобы panic в `Logger` тоже отлавливался (никогда не должен происходить, но это страховка от регрессии в slog). (3) `Logger` обёртывает `ResponseWriter` для захвата статуса — должен быть после `Recover`, чтобы Recover не перехватывал status-write. (4) `CORS` — последний из глобальных, чтобы preflight тоже логировался; OPTIONS-ответ через `Logger`/`Recover` идёт в обратном порядке корректно. (5) `RequireAuth` подключается ТОЛЬКО на protected-группах через `chi.Group + Use` (`internal/auth/transport/http/routes.go`), не глобально. |
| ADR-003 | Разделение middleware-кода на два пакета | `pkg/httpx/middleware/` (cross-cutting: Recover/Logger/CORS/RequestID) и `internal/auth/transport/http/middleware/` (auth-specific: RequireAuth) | (a) Всё в `internal/auth/transport/http/middleware/` (auth — единственный домен); (b) Всё в `pkg/httpx/middleware/` (передавать TokenVerifier интерфейсом из `pkg/`) | (1) Согласовано с пользователем (вопрос UI). (2) `RequireAuth` зависит от `usecase.TokenIssuer` и `domain.UserID` — это бизнес-граница auth-домена, нарушение слоёв при выносе в `pkg/`. (3) Cross-cutting middleware (recover/logger/cors/requestid) не зависят от auth и в фазе 2/3 будут переиспользованы в `internal/room/`, `internal/channel/`, WebSocket-handshake — естественное место `pkg/`. (4) `prompts/Go style.txt:25-28`: «Имя пакета отражает то, что пакет ПРЕДОСТАВЛЯЕТ, а не то, что он СОДЕРЖИТ» — `pkg/httpx/middleware/` предоставляет HTTP-обвязку, `internal/auth/transport/http/middleware/` предоставляет auth-обвязку. (5) Согласуется с принципом ADR-005 фичи 1.3: «адаптеры под зонтиком домена», но cross-cutting примитивы — в `pkg/`. |
| ADR-004 | CORS: явный whitelist origins без wildcard `*`; `AllowCredentials = false` | ENV `CORS_ALLOWED_ORIGINS` (CSV), default `http://localhost:5173`, валидация каждого origin как URL | (a) Wildcard `*` (один origin); (b) Wildcard с подстановкой схемы/хоста; (c) `AllowCredentials = true` сразу для будущих cookies | (1) Согласовано с пользователем (вопрос UI). (2) Wildcard `*` несовместим с `AllowCredentials: true` по spec (`https://fetch.spec.whatwg.org/#cors-protocol-and-credentials`). Хотя credentials у нас сейчас false, оставляем явный whitelist на случай миграции на cookie-auth (фаза 2/3). (3) Default `http://localhost:5173` — Vite-dev порт по умолчанию (`general_plan.md:38`). (4) Валидация на старте предотвращает копипаст-ошибки в `.env` (например, `https//example.com` без `:` будет отвергнут). (5) `AllowCredentials: false` — токены идут через `Authorization` header, не cookie; включим в фазе, когда появится кросс-доменный cookie-сценарий. |
| ADR-005 | Request-ID: UUID; принимаем `X-Request-ID` от клиента при валидности | UUID v4 через `uuid.New().String()`; валидация клиентского значения: `1 ≤ len ≤ 128`, ASCII-печатные символы; иначе генерим свой | (a) Только генерация на сервере (игнорировать клиентский header); (b) ULID/Snowflake; (c) `chi/middleware.RequestID` формат `req-...` | (1) Согласовано с пользователем (вопрос UI). (2) Клиент может прокидывать собственный request_id для трассировки между сервисами/SDK; разрешаем при валидности. (3) Жёсткая валидация (ASCII, ≤128) защищает от header injection / log poisoning (атакующий не сможет инжектить `\n\rHACK` в логи). (4) UUID v4 — стандарт, читается человеком, поддерживается grep в логах; ULID/Snowflake требуют дополнительных зависимостей (`uuid` уже есть в `go.mod`). (5) Формат `req-...` от chi/middleware — нечеловекочитаемый и без UUID-семантики; не подходит. (6) `X-Request-ID` — стандартное имя заголовка (Heroku, Cloudflare, AWS ALB), не вводим свой. |
| ADR-006 | Тип ключа в `context.Context` | Приватный `type userIDKey struct{}` + публичные хелперы `WithUserID(ctx, id)` / `UserIDFromContext(ctx) (id, bool)` | (a) `string` ключ (`"userID"`); (b) экспортируемая константа; (c) `int`-enum `type ctxKey int` | (1) `prompts/Go style.txt:51` — «не использовать `context.Value` для бизнес-данных. Только для cross-cutting: request-id, trace, **auth-principal**» — userID попадает под auth-principal. (2) Приватный typed-struct защищает от коллизий с другими пакетами (`go vet` flagging only string-keys, но идиоматично — typed-struct). (3) Хелперы `WithUserID`/`UserIDFromContext` — единственный способ положить/достать; полей не экспортируется. (4) Возвращаемое значение `(domain.UserID, bool)` вместо `(domain.UserID, error)` — нет источника ошибки кроме «нет ключа», bool достаточен. Соответствует idiom `value, ok := m[key]`. |
| ADR-007 | `RequireAuth` — фабрика, активируемая на группе, а не глобальный middleware | `r.Group(func(r chi.Router) { r.Use(authmw.RequireAuth(issuer, clock)); r.Get("/me", ...) })` | (a) Глобальный `mux.Use(RequireAuth)` со списком исключений (whitelist public paths); (b) Декоратор хендлера `WithAuth(handler)` в каждом protected-хендлере | (1) Глобальный middleware с whitelist превращает auth-логику в spaghetti: каждый раз надо помнить «забыл ли я добавить новый /public/path?». В chi это антипаттерн. (2) `chi.Group + Use` — идиоматичный chi-способ; делает разделение public/protected явным в коде (`internal/auth/transport/http/routes.go`). (3) Декоратор `WithAuth(handler)` — лишняя обёртка вокруг каждого хендлера, шум при чтении. (4) Фабрика принимает `usecase.TokenIssuer` и `usecase.Clock` — те же зависимости, что нужны в фазе 2 для `/rooms`, `/channels` (они переиспользуют тот же `RequireAuth`, конфигурируя разные группы). |
| ADR-008 | `Recover`: ловит panic, пропускает `http.ErrAbortHandler`, корректно работает после `WriteHeader` | `defer func() { if v := recover(); v != nil { if errors.Is(v, http.ErrAbortHandler) { panic(v) }; …slog.Error… ; if !alreadyWroteHeader { WriteJSONError(500) } } }()` | (a) Не пропускать `ErrAbortHandler` (текущий стандарт `chi/middleware.Recoverer` — пропускает); (b) Всегда пытаться писать 500, даже после `WriteHeader` (приведёт к усечённому ответу); (c) `panic(v)` без логирования | (1) `http.ErrAbortHandler` — стандартный механизм net/http для прерывания запроса без обработки (используется, например, при WS-handshake). Recover должен пропускать его для совместимости. (2) Запись 500 после `WriteHeader` — нарушение HTTP-протокола; вместо этого логируем `slog.Warn("panic after WriteHeader, response truncated")` и завершаем. (3) Без логирования panic — теряем контекст ошибки; обязательно `slog.Error` со stack trace, request_id, method, path. (4) Логирование stack trace через `runtime/debug.Stack()` (stdlib). |
| ADR-009 | Отказ от пакета `chi/middleware` целиком | Используем `chi.Router` для роутинга, но НЕ `chi/middleware` для middleware-обвязки | (a) Использовать `chi/middleware.RequestID/Recoverer/Logger`, кастомизировать форматы вывода; (b) Гибрид: chi для recover, своё для cors | (1) chi/middleware заточен под определённый формат (text-логи, `req-` префикс ID, plain-text 500). Адаптация под наш JSON-envelope и slog требует обёрток, что съедает экономию строк кода. (2) Свои реализации без зависимостей даёт полный контроль над форматом полей логов (`request_id`, `method`, `path`, `status`, `duration` — единый набор). (3) chi-маршрутизация и chi-middleware — разные модули; отказ от middleware-модуля не влияет на роутинг. |
| ADR-010 | Регистр префикса `Bearer ` | Case-sensitive: только `Bearer ` (CamelCase) | (a) Case-insensitive: `Bearer`/`bearer`/`BEARER` через `strings.EqualFold`; (b) Trim space перед matching | (1) Совпадает с поведением 1.3 (`docs/1_3_auth_domen/03-decisions.md`, ADR-009): «принимаем только `Bearer ` для предсказуемости». RFC 7235/6750 требует `Bearer` строго CamelCase в схеме, но клиенты часто шлют `bearer`. (2) Тесты 1.3 (`TestMeHandler_BadScheme` — `Authorization: Basic ...`) ожидают строгого matching. (3) Если в будущем понадобится терпимость — её можно добавить точечно (`strings.HasPrefix(strings.ToLower(auth), "bearer ")`) с одной правкой `RequireAuth.go`, без изменения контракта. (4) Сейчас все тестовые `.http`-файлы (`manual_qa/1_3_auth/04_me.http`) используют CamelCase. |
| ADR-011 | Единый JSON-envelope ошибок через `pkg/httpx.WriteJSONError` | Helper `WriteJSONError(w, status int, code, message string)` в `pkg/httpx/jsonerror.go`; `error_mapper.go:writeError` и `RequireAuth`/`Recover` оба используют его | (a) Дублировать сериализацию envelope в каждом middleware; (b) Перенести `error_mapper.go` целиком в `pkg/httpx/` | (1) Дублирование — два места, где описана JSON-форма; рассинхрон неизбежен при изменениях. (2) `error_mapper.go` остаётся в `internal/auth/transport/http/`, потому что маппинг доменных ошибок — auth-specific (`AUTH-001..012`). Перенос в `pkg/` нарушит правило слоёв. (3) `WriteJSONError` — низкоуровневая утилита: status + code + message → JSON. Ничего auth-специфичного. (4) Контракт пакета `pkg/httpx`: единственная экспортируемая функция плюс types для request_id. Минимальная public API. |
| ADR-012 | `Logger` не логирует тела запросов/ответов | Только метаданные: `method`, `path`, `status`, `duration`, `request_id`, `remote_ip`, `user_agent` | (a) Логировать body на DEBUG-уровне; (b) Логировать только при ошибках (4xx/5xx) | (1) `prompts/Go style.txt:94`: «Не логировать PII и секреты. Пароли, токены, email по возможности маскировать». Тела регистрации/логина содержат пароли, тела refresh — refresh-токен. (2) Маскирование на уровне middleware невозможно без знания формата тела (это нарушает разделение слоёв — middleware не должен знать про DTO). (3) При нештатных ситуациях есть Recover, который логирует stack trace; для обычных 4xx/5xx — request_id связывает access-log с upstream-логами use case (где доменные ошибки логируются с осмысленным контекстом). (4) `remote_ip` берётся из `r.RemoteAddr` (без интерпретации `X-Forwarded-For` — мы за прямым подключением до фазы deploy с reverse-proxy). (5) `user_agent` — из `r.UserAgent()`; не PII. |
| ADR-013 | `UserIDFromContext` возвращает `(UserID, bool)`, не `(UserID, error)` | `func UserIDFromContext(ctx context.Context) (domain.UserID, bool)` | (a) `(UserID, error)` с sentinel `ErrNoUserID`; (b) `*UserID` с nil-pointer-проверкой | (1) Идиома Go — `value, ok := m[key]` для optional retrieval. Хелпер контекста — частный случай. (2) Источник истины об ошибке — RequireAuth, который вернул бы 401 ДО хендлера. Если хендлер достигнут без userID, это **ошибка маршрутизации** (хендлер в неверной группе), а не runtime error. Защитная ветка `if !ok { writeError(...) }` это покрывает. (3) `*UserID` с nil-проверкой — не подходит, потому что `domain.UserID` — value object (значение, не указатель). Передача указателя на VO — лишний уровень indirection. |

## Риски и митигация

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Утечка чувствительных данных через access-log (пароли в URL, токены в headers) | High | (1) `Logger` логирует только определённый whitelist полей (см. ADR-012). (2) `Authorization` header в логи **не попадает**. (3) Пароли в URL не предусмотрены контрактом (`08-api-contract.md`). (4) Тест `TestLogger_DoesNotLogAuthorizationHeader` явно проверяет. |
| Header injection через `X-Request-ID` от клиента (`\r\n` в значении) | Medium | RequestID middleware валидирует ASCII-печатные символы и длину ≤128; невалидное значение игнорируется. Тест `TestRequestID_RejectsCRLFInjection` покрывает. |
| Двойной `WriteHeader` после panic (panic после уже-отправленного header) | Low | Recover проверяет `headerWritten` через обёртку `responseWriter`. Не пишет 500 повторно. Логирует `slog.Warn("panic after WriteHeader, response truncated")`. Тест `TestRecover_PanicAfterWriteHeader` покрывает. |
| `http.ErrAbortHandler` пожран Recover'ом → нарушение semantics net/http | Medium | Recover проверяет `errors.Is(v, http.ErrAbortHandler)` и пере-paniкует, как стандартный chi/Recoverer. Тест `TestRecover_PassesAbortHandler` покрывает. |
| CORS-конфиг с невалидным origin при старте → запросы фронта блокируются молча | Medium | `config.Load` валидирует каждый origin как URL (`<scheme>://<host>[:port]`). Невалидный → fail-fast `CONFIG-006`. Тест `TestConfig_Load_InvalidCORS_*`. |
| Замедление сервера из-за `slog.Info` на каждом запросе | Low | `slog` JSON-handler — структурированный, быстрый (десятки µs на запись). На MVP-нагрузке (≤100 RPS) незаметно. Если понадобится — отключение через `LOG_LEVEL=warn` (открытый вопрос). |
| Браузер ожидает `Access-Control-Allow-Credentials: true`, а у нас false → cross-domain cookie не отправится | Low | В фазе 1.4 сессии не на cookies, а на `Authorization` header. AllowCredentials=true включаем при появлении cookie-сессий (фаза 2/3). |
| Утечка userID в логи при нештатных условиях (например, сериализация структуры с UserID) | Low | userID — это публичная UUID-строка, не PII (привязка к личности — отдельная таблица users.email/username). Логирование `user_id` в access-log допустимо. |
| Регрессия 1.3-тестов после переезда `MeHandler` на middleware | Medium | Существующие 5 тестов `MeHandler_*` (`docs/1_3_auth_domen/04-testing.md`) запускаются против собранного `chi.Router` с новым middleware. Все ожидания (статус, code) остаются прежними. Test plan в `04-testing.md` явно перечисляет переходы. |
| Глобальный middleware ловит запросы, не относящиеся к `/api/v1` (когда в фазе 5 появится `web/`) | Low | На фазе 1.4 единственный subroute — `/api/v1`. Когда появится статика `web/`, глобальные `RequestID`/`Recover`/`Logger`/`CORS` всё равно нужны (логирование статики и preflight). Конфликта нет. |
| panic-у в Recover-middleware (например, в slog.Error) — recursive panic | Critical | `slog`-вызовы в Recover защищены: `slog.Error` сам по себе panic-free для JSON-handler. Если случится — net/http прокидывает на уровень `http.Server.ErrorLog`. На MVP не покрываем тестом (требует мок-логгер с panic-инъекцией). |
| Неконтролируемый рост cardinality логов (если в `path` попадают user-controlled данные) | Low | `path` берётся из `r.URL.Path` — после chi-маршрутизации, но до этого middleware. В chi-роутах используется `:id` параметризация (фаза 2+), но `r.URL.Path` оставит конкретное значение. На фазе 1.4 пути фиксированы (`/api/v1/auth/{register,login,refresh,me}`, `/api/v1/health`) — cardinality ограничена. В фазе 2 пересмотрим (возможно, добавим `route_pattern` через `chi.RouteContext`). |

## Open Questions

- [x] **OQ-1.** Логировать ли `user_id` в access-log на authenticated-запросах?
  - **Ответ:** да. `Logger` middleware читает `user_id` из ctx через `authmw.UserIDFromContext(ctx)` (если `ok == true`), добавляет в `slog.Info`. На public-запросах поле отсутствует. Это требует, чтобы `Logger` импортировал `internal/auth/transport/http/middleware`, что нарушает иерархию (cross-cutting → auth-specific). **Решение:** `Logger` принимает опциональный hook-функцию `func(ctx) []slog.Attr` через параметр, и в `cmd/server/main.go` композиция передаёт `authmw.UserIDFromContext` как hook. Это сохраняет независимость `pkg/httpx/middleware/Logger` от auth-домена. См. реализацию в `01-architecture.md`.
- [x] **OQ-2.** Логировать `User-Agent` и `Remote-IP`?
  - **Ответ:** да (см. ADR-012). Это не PII, помогает в отладке.
- [x] **OQ-3.** Поддерживать `X-Forwarded-For` для `Remote-IP`?
  - **Ответ:** нет в фазе 1.4. До deployment'а с reverse-proxy `r.RemoteAddr` — корректное значение. Когда появится reverse-proxy — отдельный middleware `RealIP` в `pkg/httpx/middleware/`, опциональная активация в `cmd/server/main.go`.
- [x] **OQ-4.** `LOG_LEVEL` env-переменная?
  - **Ответ:** не в фазе 1.4. `slog.LevelInfo` хардкод (как сейчас в `cmd/server/main.go:36`). Если понадобится — отдельная задача с парой строк в `config/config.go`.
- [ ] **OQ-5.** Метрики Prometheus / OpenTelemetry?
  - Не в фазе 1.4. Отдельная фича «observability», требует выбора либы и согласования.
  - **Откладывается** до явного запроса.
- [ ] **OQ-6.** Rate-limiting на `/auth/login` и `/auth/refresh`?
  - Не в фазе 1.4. `general_plan.md:114-118` middleware-задача rate-limit не упоминает.
  - Реализация (если потребуется): отдельный middleware на public-группе с in-memory counter (либо Redis в фазе 3+).
  - **Откладывается** до фазы 2/3 или явного запроса.
- [x] **OQ-7.** `AllowedHeaders` в CORS — фиксированный список или `*`?
  - **Ответ:** фиксированный: `Authorization, Content-Type, X-Request-ID`. Список явный, проверяется тестом `TestCORS_PreflightHeaders`. Wildcard `*` — нечёткая семантика, отказываемся.
- [x] **OQ-8.** Обрабатывать ли `MethodNotAllowed`/`NotFound` через JSON-envelope?

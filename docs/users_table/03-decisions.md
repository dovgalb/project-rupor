# Решения по схеме `users`

## Решения

| # | Решение | Выбор | Альтернативы | Обоснование |
|---|---------|-------|--------------|-------------|
| 1 | Тип первичного ключа | `uuid` со значением по умолчанию `gen_random_uuid()` | `bigserial` / клиентская генерация UUID | Расширение `pgcrypto` уже подключено миграцией `migrations/0001_init.up.sql:4`. UUID согласуется с конвенцией id-маппинга в `prompts/RepoModel.txt:118-122` (`uuid.UUID` ↔ `domain.UserID`) и не привязывает домен к автоинкременту БД. |
| 2 | Тип столбца `email` | `citext` | `text` + `CREATE UNIQUE INDEX ... (lower(email))` | `citext` даёт case-insensitive уникальность одним типом и одним обычным `UNIQUE`-ограничением — это совместимо с конвенцией имени `users_email_key` из `prompts/RepoModel.txt:138-140`. Альтернатива требует функционального индекса с произвольным именем и нормализации в каждом запросе. |
| 3 | Тип столбца `username` | `text` + `CHECK length(username) BETWEEN 3 AND 32`, `UNIQUE` | `varchar(32)` / отдельная нормализация в БД | В Postgres `text` и `varchar(n)` физически идентичны; явный `CHECK` яснее и легче меняется. Регистрозависимость уникальности оставлена БД; нормализация (если понадобится) — задача доменного VO в фазе 1.3, а не миграции. |
| 4 | Тип столбца `password_hash` | `text NOT NULL` | `varchar(60)` (фикс. длина bcrypt) | Алгоритм хеширования может смениться (argon2id и т.п.), фиксированная длина создала бы лишнюю зависимость. План явно предписывает bcrypt только в фазе 1.3 (`general_plan.md:108`), но миграция не должна это закреплять. |
| 5 | Тип столбца `created_at` | `timestamptz NOT NULL DEFAULT now()` | `timestamp` без зоны, проставление времени из приложения | `timestamptz` хранит UTC и корректно сериализуется в любой клиентский часовой пояс — это снимает класс багов сравнения времён. `DEFAULT now()` упрощает первый INSERT в фазе 1.3 (приложение может не передавать поле). |
| 6 | Имена ограничений | Дефолтные: `users_pkey`, `users_email_key`, `users_username_key` | Кастомные с префиксом домена (`auth_users_email_unique`) | `users_email_key` явно ожидается в `prompts/RepoModel.txt:138-140` для маппинга unique-violation в `domain.ErrEmailAlreadyTaken`. Дефолтные имена Postgres детерминированы и не требуют документировать схему именования. |
| 7 | Индексы на `email` / `username` | Покрываются автоматически уникальными ограничениями (Postgres создаёт b-tree индекс под каждый `UNIQUE`) | Отдельные `CREATE INDEX` | План требует «индексы на email/username» (`general_plan.md:103`); `UNIQUE` это требование закрывает. Дублирование `CREATE INDEX` поверх `UNIQUE` создаёт два одинаковых индекса. |
| 8 | Soft delete (`deleted_at`) | Не добавлять | `deleted_at timestamptz NULL` | План MVP не требует удаления пользователей; добавление поля «на будущее» противоречит правилу `CLAUDE.md` «не проектировать под гипотетические требования». Если потребуется — отдельная миграция. |
| 9 | Поле `status` | Не добавлять | `status text NOT NULL DEFAULT 'active'` | Поле `status` фигурирует в примере `userRow` в `prompts/RepoModel.txt:46-52`, но это иллюстрация маппинга, а не часть scope задачи 1.2 (`general_plan.md:101`). Добавим, когда появится явное требование (бан, верификация и т.п.). |
| 10 | Расширение `citext` | Подключается этой же миграцией (`CREATE EXTENSION IF NOT EXISTS citext`) и отключается в down | Подключить в `0001_init`, ретроспективно | `0001_init` уже накачен на dev-БД; ретроактивно менять прошлые миграции запрещено правилами `golang-migrate`. Расширение принадлежит этой фиче — добавляем рядом с таблицей. |
| 11 | Имя slug миграции | `0002_users` | `0002_create_users_table` / `0002_init_auth` | Соответствует стилю `0001_init` (короткий slug по существу). Префикс `0002` — следующий свободный (см. research `## Состояние ветки`). |
| 12 | Изменения вне `migrations/` | Никаких | Заодно настроить `sqlc.yaml`, добавить queries | `sqlc.yaml` сейчас пуст (`sql: []`); его настройка — часть задачи 1.3 «домен auth» (`general_plan.md:105-112`). В рамках 1.2 не трогаем, чтобы PR оставался single-purpose. |

## Риски и митигация

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Down-миграция не дропает `citext`, и после `migrate-down` остаётся «висящее» расширение | Low | В down-миграции явный `DROP EXTENSION IF EXISTS citext`. Если `citext` потребуется другой фиче — она объявит своё `CREATE EXTENSION IF NOT EXISTS`. |
| Down-миграция падает, если в БД уже есть данные | Low | Down предназначен для разработческого отката; на проде down не применяется. Документируется как dev-only. |
| Замечание о том, что `citext` несовместим с некоторыми операциями (например, регистрозависимым поиском) | Low | В рамках MVP email сравнивается только на равенство; регистрозависимый поиск по email не нужен. |
| Имя `users_email_key` не совпадёт с реальным после миграции (Postgres усечёт длинное имя) | Low | Имя короткое (длина ≤ 63 символов NAMEDATALEN), проблема не возникает. Проверяется глазом после `migrate-up` через `\d users` или `pg_constraint`. |
| Будущая фича потребует поле `status` / `deleted_at` — придётся писать ещё миграцию | Low | Это норма; `golang-migrate` ровно для этого. Решения 8–9 фиксируют сознательный отказ от prematurity. |

## Open Questions

- [x] Регистрозависимость `username`?
  - **Ответ:** регистрозависимая в БД. Если домен потребует case-insensitive уникальность (`Bogdan` и `bogdan` — один пользователь), это решит VO `Username` в задаче 1.3 нормализацией перед сохранением.
- [x] Длина `username`?
  - **Ответ:** 3–32 символа, ограничение через `CHECK` на уровне БД. Цифру 32 берём как общепринятый Discord-подобный лимит; точная политика валидации (разрешённые символы, lowercase) — в VO `Username` в задаче 1.3.
- [x] Часовой пояс `created_at`?
  - **Ответ:** `timestamptz`, хранится в UTC.
- [ ] Нужно ли уже сейчас зарезервировать поле `email_verified_at` под подтверждение почты? — отложено до появления требования по верификации; в scope MVP его нет.

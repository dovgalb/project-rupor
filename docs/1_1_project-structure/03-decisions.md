# 03 — Decisions (Decision View)

## Решения

| # | Решение | Выбор | Рассмотренные альтернативы | Обоснование |
|---|---------|-------|----------------------------|-------------|
| ADR-001 | Структура слоёв `internal/<домен>/{domain,usecase,transport/http,repository/postgres}/` физически создаётся через `.gitkeep` | Все 6 доменов из `general_plan.md` × 4 слоя = 24 пустые папки | (a) Создавать папки лениво при добавлении домена; (b) Раскладка `internal/<слой>/<домен>/` (слой → домен) | (1) Терминология фиксирована в `prompts/Architecture Layers.txt:118-123`, отклонения недопустимы. (2) `general_plan.md:5-25` уже перечисляет шесть доменов — список не меняется. (3) Раскладка «домен → слой» соответствует `CLAUDE.md:8-19` — отклонение от документации без причины недопустимо. |
| ADR-002 | `cmd/server/main.go` — единственная точка входа в этой фиче | Один бинарник `bin/server` | (a) Несколько бинарников (`cmd/server`, `cmd/migrate`, `cmd/cli`); (b) Бинарник `cmd/migrate` поверх `golang-migrate` API | (1) `CLAUDE.md:7` явно фиксирует `cmd/server/` как точку входа. (2) `golang-migrate` есть как самостоятельный CLI — оборачивать его в свой бинарник без причины — лишний код. (3) MVP не требует CLI-команд. Решение пересматривается при появлении необходимости в seed-командах или admin-CLI. |
| ADR-003 | API-сервер запускается локально через `make run`, не через `docker-compose` | В `docker-compose.yml` только `postgres`, нет сервиса `api` | (a) Запихнуть `api` в compose с Dockerfile multi-stage; (b) Tilt/Skaffold для горячей перезагрузки | (1) Локальная сборка через `go run` даёт быстрый цикл `<1с`, Docker-build добавит 10–30с на каждое изменение. (2) Dockerfile для прода — отдельная фича: на MVP нет деплоя. (3) `nhooyr.io/websocket` и chi легко работают на хосте. (4) Контейнеризация PostgreSQL изолирует данные между разработчиками — это единственное, что реально надо контейнеризировать. |
| ADR-004 | Конфигурация только через env, без YAML/TOML/JSON-файлов | `config.Load(Lookuper)` читает env через интерфейс | (a) `viper` с поддержкой YAML+env+flags; (b) `envconfig` (Kelsey Hightower); (c) Go-flags + env fallback | (1) `prompts/Go style.txt:84-87` запрещает `config.yaml`/`config.toml` явно. (2) `prompts/Go style.txt:111-117` запрещает новые зависимости без согласования — `viper`/`envconfig` это новые зависимости. (3) `os.LookupEnv` + `strconv.Atoi` достаточно для трёх переменных, никакой магии не нужно. (4) Интерфейс `Lookuper` обеспечивает тестируемость без `os.Setenv` (`prompts/Tests Style.txt:204-211` запрещает использовать env-переменные в тестах через глобальный setenv). |
| ADR-005 | sqlc + golang-migrate, без ORM | `sqlc.yaml` версии 2, заготовка с закомментированным блоком per-domain | (a) GORM; (b) ent; (c) Bun; (d) самописный query builder | (1) `prompts/Go style.txt:97-101` явно запрещает ORM. (2) `prompts/RepoModel.txt:163-166` — sqlc-генерация типизированных методов не тащит SQL в `domain/`. (3) `general_plan.md:71-73` фиксирует sqlc и golang-migrate в стеке. (4) `CLAUDE.md:33` подтверждает выбор. |
| ADR-006 | `/api/v1/health` не зависит от БД | Возвращает `{"status":"ok"}` всегда, пока сервер жив | (a) `/health` проверяет соединение с PostgreSQL через `db.PingContext`; (b) Раздельные `/livez` и `/readyz` (k8s convention) | (1) В этой фиче БД ещё не используется в Go-коде — некорректно проверять. (2) `livez` vs `readyz` имеет смысл только при деплое в k8s — это отдельная фича. (3) В Фазе 1.2+ можно добавить `/api/v1/healthz` с глубоким чеком, не ломая `/health`. (4) Простой health-check валидирует, что HTTP-сервер вообще поднялся — этого достаточно для smoke. |
| ADR-007 | `sqlc.yaml` создаётся с закомментированным шаблоном блока, фактических `sql:`-блоков нет | На уровне репо есть валидный `sqlc.yaml` v2 с пустым массивом `sql: []` или 1 dummy-блоком | (a) Не создавать `sqlc.yaml` до первой миграции с таблицами; (b) Создать один блок per-domain заранее, с пустыми `queries:` дирами | (1) Фича обещает наличие `sqlc.yaml` в scope. (2) Пустой массив `sql: []` валиден для версии 2. (3) Шесть пустых блоков создадут шесть пустых сгенерированных пакетов на `sqlc generate` — мусор. (4) Закомментированный шаблон в `sqlc.yaml` показывает разработчику, как добавлять блок per-domain (UX-решение). |
| ADR-008 | Минимальный набор линтеров в `.golangci.yml` | `govet`, `staticcheck`, `errcheck`, `ineffassign`, `unused`, `gofmt`, `goimports` | (a) Полный список из `golangci-lint`; (b) Включить `revive`, `gocyclo`, `gosec`, `misspell` сразу | (1) `prompts/Go style.txt:122` требует `gofmt`/`go vet`/`golangci-lint run`, но не уточняет набор. (2) Минимальный набор покрывает 95% реальных багов. (3) Расширенные линтеры легко добавлять по мере роста — обратная задача (отключить агрессивный линтер) сложнее. (4) `gosec` добавим, когда появятся auth/JWT — тогда он будет полезен. |
| ADR-009 | Initial-миграция `0001_init.up.sql` создаёт только `CREATE EXTENSION IF NOT EXISTS "uuid-ossp"` (или `pgcrypto`) | Один SQL-файл с одной командой и парный `down`-файл с `DROP EXTENSION` | (a) Пустой `0001_init.up.sql`; (b) Сразу разделить на `0001_extensions`, `0002_users` и т.д. | (1) Расширение `uuid-ossp` или `pgcrypto` нужно для генерации UUID на стороне БД (`general_plan.md:5-25` использует UUID для всех ID). (2) Применение `gen_random_uuid()` через `pgcrypto` — современный путь, `uuid-ossp` устарело — выбор `pgcrypto`. (3) Пустая миграция бесполезна и не валидируется на CI. (4) Бизнес-таблицы `users`/`rooms` идут в Фазе 1.2 как отдельные миграции `0002_*`/`0003_*`. |
| ADR-010 | `golang-migrate` устанавливается локально как CLI, не через `docker compose run` | `Makefile` вызывает `migrate` напрямую | (a) Запускать `migrate` через `docker compose run --rm migrate ...`; (b) Завернуть в свой Go-бинарник | (1) Локальный CLI быстрее, не зависит от `docker compose up postgres`. (2) Установка тривиальна: `brew install golang-migrate` или `go install`. (3) В CI используем `actions/setup-go` + `go install`. (4) В `Makefile` нет смысла оборачивать вызов одной строки в compose. |
| ADR-011 | CI на GitHub Actions, один workflow `.github/workflows/ci.yml` | Триггеры `push: [main]`, `pull_request: [main]` | (a) Несколько workflow (`build.yml`, `test.yml`, `lint.yml`) с матрицей; (b) GitLab CI / CircleCI; (c) Только pre-commit hook без CI | (1) Один workflow с тремя последовательными шагами проще читать и дешевле по runner-минутам. (2) GitHub Actions бесплатен на public repos и щедр на private. (3) Pre-commit hook не заменяет CI — его легко обойти `--no-verify`. |
| ADR-012 | `chi` v5 — единственная сторонняя зависимость в `go.mod` после фичи | `github.com/go-chi/chi/v5` | (a) Только `net/http` ServeMux; (b) `gorilla/mux`; (c) `gin`/`echo` | (1) `CLAUDE.md:33` и `general_plan.md:71` фиксируют `chi`. (2) `net/http.ServeMux` Go 1.22+ умеет path patterns, но не имеет middleware groups, чем chi удобен для будущих `auth`-чейнов. (3) `gorilla/mux` deprecated. (4) `gin`/`echo` — heavier и не в стеке. |
| ADR-013 | `.env.example` в корне, в `.gitignore` запрет `.env` | Шаблон с дефолтами для dev: `DATABASE_URL=postgres://rupor:rupor@localhost:5432/rupor?sslmode=disable`, `JWT_SECRET=change-me-in-prod`, `SERVER_PORT=8080` | (a) Не коммитить шаблон, документировать в README; (b) Использовать direnv (`.envrc`); (c) Использовать `dotenv-go` загрузку из `.env` в коде | (1) `prompts/Go style.txt:84-87` — конфиг только через env, но не запрещает источник env. (2) Загрузка из `.env` в коде — лишняя зависимость (`godotenv`), запрещено `prompts/Go style.txt:111-117`. (3) Разработчик `source .env` или `direnv allow` — это его инструмент. (4) Шаблон в репо — UX-стандарт. |
| ADR-014 | Graceful shutdown с таймаутом 5с, без двойного SIGINT | `signal.NotifyContext` + `srv.Shutdown(ctxWithTimeout(5s))` | (a) Без graceful (просто `os.Exit`); (b) Двойной SIGINT — второй убивает принудительно; (c) Таймаут 30с | (1) HTTP-запросы в этой фазе короткие (health-check) — 5с с большим запасом. (2) Двойной SIGINT — UX-фича для CLI, не критична для сервера; добавим в Фазу 3 при WebSocket-долгожителях, если понадобится. (3) 30с слишком долго для dev-цикла, 5с балансирует. |

## Риски и митигация

| Риск | Влияние | Митигация |
|------|---------|-----------|
| 24 пустые папки `.gitkeep` создают шум в git и навигации | Low | `.gitkeep` — индустриальный стандарт, редакторы и `tree` обычно их фильтруют. Альтернатива (создавать папки лениво) приводит к рассинхрону между документацией и реальностью. |
| Конфигурация без `viper` означает пере-имплементацию `.env` поддержки в будущем | Low | На этой фазе `Lookuper` интерфейс — точка расширения. Добавить `dotenvLookuper` рядом с `osLookuper` — 20 строк, без новой зависимости. |
| `sqlc.yaml` с пустым `sql: []` может оказаться невалидным | Low | Проверка на CI: шаг `sqlc generate --dry-run` (или просто `sqlc compile`). Если массив `sql: []` не принимается, переключаемся на закомментированный шаблон с одним блоком и `# uncomment when first domain arrives`. |
| `make run` без поднятой PostgreSQL не падает (БД не используется), но в Фазе 1.2 — упадёт неожиданно | Medium | `/api/v1/health` намеренно не зависит от БД (ADR-006). При добавлении БД-зависимых эндпоинтов добавим pre-flight check в `main()` с понятной ошибкой. |
| CI на push в `feature/*` ветки расходует runner-минуты на каждый push | Low | Триггер только на `push: [main]` и `pull_request: [main]`. Для feature-веток — push без CI до открытия PR. Если станет проблемой — добавим `paths-ignore` для документов. |
| Установка `golang-migrate` CLI требует ручного шага у нового разработчика | Medium | Документируем в `README.MD` команду установки (`brew install golang-migrate` / `go install`). В CI ставим через `go install` в `setup`-шаге. Альтернатива (compose-обёртка) — рассматривается в открытом вопросе. |
| `pgcrypto` против `uuid-ossp` — выбор может оказаться неверным для прода | Low | `pgcrypto` встроено в `postgres:16-alpine`, не требует docker-extension. `uuid-ossp` тоже встроено, но команда `gen_random_uuid()` из `pgcrypto` стала стандартом в Postgres 13+. Откат — переписать одну строку в `0001_init.up.sql`. |
| Запрет ORM может привести к переписыванию `sqlc`-блоков при сложных join-ах | Low | `prompts/RepoModel.txt:165-167` явно ставит ограничение «лучше два запроса, чем мутный join». Это уже митигировано стандартом. |
| Линт-конфиг `.golangci.yml` с минимальным набором пропустит security-issue до Фазы 1.2 | Medium | На Фазе 1.2 (auth/JWT) добавим `gosec` отдельным PR. До тех пор кода с уязвимыми паттернами нет. |

## Open Questions

- [ ] **Q1.** Делать ли `make migrate-up` через `docker compose run --rm migrate` или требовать локально установленного `migrate` CLI? Решено в ADR-010 в пользу локального CLI; вопрос остаётся открытым на случай, если новый разработчик жалуется на сложность установки.
- [ ] **Q2.** Включать ли `gosec` в `.golangci.yml` уже сейчас или ждать появления auth-кода? Текущий выбор — ждать (ADR-008). Подтвердить с пользователем.
- [ ] **Q3.** `sqlc.yaml` со схемой `sql: []` — валиден ли он для sqlc v2? Проверка делается на этапе плана (см. `04-testing.md`). Если невалиден — переключаемся на закомментированный шаблон.
- [ ] **Q4.** Двойной SIGINT для принудительного shutdown — нужен ли в Фазе 1.1 или ждём WebSocket в Фазе 3? Текущий выбор — ждать (ADR-014).
- [ ] **Q5.** Лимит порта `1..65535` или `1024..65535` (запрет привилегированных портов на dev-машине)? Текущий выбор — `1..65535`, разработчик сам отвечает за `setcap`/`sudo`.
- [ ] **Q6.** Триггер CI только на `main` или на все ветки? Текущий выбор — `[main]` + PR, экономит runner-минуты, но даёт обратную связь только на PR. Альтернатива: `push: ['**']` + `paths-ignore: ['docs/**', '*.md']`.
- [ ] **Q7.** Нужен ли `Dockerfile` для Go-сервера в этой фиче для воспроизводимости CI? Текущий выбор — нет (ADR-003, ADR-011: CI собирает на runner-е). Появится с production-деплоем.
- [ ] **Q8.** Имя БД и пользователя в dev-среде: `rupor`/`rupor` или что-то более специфичное? Текущий выбор — `rupor`/`rupor`/`rupor` (user/pass/db). Меняется одной строкой в `.env.example` и `docker-compose.yml`.

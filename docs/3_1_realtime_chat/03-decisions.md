# 03 — Decisions (Decision View)

Решения, альтернативы, риски, open questions. ADR-формат сжат до таблицы для скорости MVP.

## Решения

| # | Решение | Выбор | Рассмотренные альтернативы | Обоснование |
|---|---|---|---|---|
| D-01 | Где живёт порт проверки прав для chat | Зеркальный порт `chat/usecase.MembershipQuery` (отдельный интерфейс с собственным `RoleRequirement`); реализация в `internal/room/repository/postgres/membership_query.go` рядом с уже существующим `MembershipQueryAdapter` для channel | (a) импорт `channel/usecase.MembershipQuery` напрямую; (b) общий пакет `internal/membership/`; (c) дублирование SQL в chat-репо | Сохраняет независимость chat от channel (`arch_test.go:337-362` запрещает channel/usecase→room, тот же принцип распространяется на chat). Реализация одной строкой делегируется уже работающей в `room/repository/postgres/membership_query.go:29-66` SQL-логике. Расширение `arch_test.go` минимальное — копия `TestArchitecture_RoomRepoMayImplementChannelPort` (`arch_test.go:259-280`) для chat. |
| D-02 | Архитектура WebSocket-слоя | `pkg/websocket/` — доменно-агностичный hub (`Hub`, `Conn`, `Topic`, `Upgrade`); `internal/chat/transport/ws/` — chat-handler с парсингом событий | (a) всё в `internal/chat/transport/ws`; (b) всё в `pkg/websocket`; (c) `internal/transport/ws/` как общий пакет | Зеркалит существующее разделение `pkg/httpx` (агностичный) + `internal/<domain>/transport/http` (доменный). Готовит почву для voice signaling в фазе 4: voice использует тот же hub, добавляет свой handler. `pkg/websocket` не импортирует `internal/*` (правило `arch_test.go:162-187`). |
| D-03 | Concurrency model в `Conn` | `sync.Mutex` на write; read — однопоточный из owning горутины | (a) канал-баззер с одной writer-горутиной; (b) lock-free через atomic | nhooyr.io/websocket требует сериализации writes, но допускает concurrent reads/writes из разных горутин при условии mutex'а на write. Канал-баззер тянет дополнительный goroutine на каждый conn (×N коннектов = ×N горутин) при минимальной выгоде; на MVP-нагрузке мьютекс достаточен. Подтверждение паттерна — README nhooyr.io/websocket. |
| D-04 | Edit/delete сообщений в MVP | Не реализуется. `Message` — append-only, без `updated_at`, `deleted_at`. | Сразу заложить редактирование/удаление с polymorphic-эвентами | Из `general_plan.md:24` («в MVP без редактирования/удаления — добавим позже»). Упрощает домен, таблицу `messages`, и WS-протокол. Будущее редактирование добавит миграцию `0009_messages_edited_at.up.sql` и события `message.edited`/`message.deleted` без ломки текущего контракта. |
| D-05 | Проверка типа канала (text vs voice) при отправке | В chat-репозитории — отдельный sqlc-запрос `GetChannelKind(channel_id)` возвращает `(room_id, kind, exists)`. Use case `SendMessage` проверяет: канал существует (`ErrChannelNotFound`) → канал text (`ErrChannelNotText`) → права в этой комнате через `MembershipQuery.Require(channelID, userID, RoleAnyMember)`. | (a) хранить kind в Message и проверять в домене (но это нарушает single-source-of-truth: kind принадлежит channel); (b) FK на kind не существует; (c) проверка только при подписке без проверки при send (риск race) | Канал — внешняя по отношению к chat сущность. Проверка типа выполняется на границе usecase, чтобы домен не зависел от внешних схем. Один дополнительный round-trip к БД — приемлемая цена, т.к. в крупных приложениях этот lookup закэширован, а в MVP — пренебрежимо. `MembershipQuery.Require` получает `channelID`, не `roomID`: адаптер сам резолвит roomID через тот же запрос (см. `06-repo-model.md`). |
| D-06 | Сигнатура `MembershipQuery.Require` | Принимает `channelID`, не `roomID`. Адаптер делает JOIN `channels` ↔ `room_members` за один запрос. | Передавать `roomID`, заставлять use case сначала резолвить `roomID` через `ChannelOf` | Сокращает количество round-trip'ов с 2 до 1 в типичном пути. Адаптер `MembershipQueryAdapter` (`room/repository/postgres`) знает оба домена и может JOIN'ить. На случай специфичных операций (например, операции в комнате без указания канала — `member.joined` от `room/usecase`) — отдельный метод `RoomEventsPublisher.PublishMemberJoined(roomID, ...)`. |
| D-07 | Где живёт публикация `member.joined` | Объявляется порт `room/usecase.RoomEventsPublisher` в room-домене; реализация в `pkg/websocket.Hub`. Биндинг в `cmd/server/main.go`. | (a) room/usecase напрямую импортирует `pkg/websocket` (нарушает clean arch); (b) chat подписывается на room через event bus в БД (overkill для MVP); (c) только chat шлёт events, room ничего не знает (нет события `member.joined`) | Сохраняет правило «usecase объявляет порт, адаптер реализует». Минимальное изменение `room/usecase` — добавление одного поля в `JoinByCode` и одного вызова в конце Execute. Не вводит транзакционность publish'а (best-effort). |
| D-08 | Транзакционность Save + Publish | Не транзакционно. Save в БД → если ok, Publish (best-effort, ошибка логируется и игнорируется) | (a) outbox-таблица с фоновым воркером; (b) Postgres LISTEN/NOTIFY | Outbox — оверинжиниринг для MVP. LISTEN/NOTIFY завязывает hub на конкретный driver. Best-effort приемлем, потому что при дисконнекте клиент дотянет историю через REST `ListMessages`. Тесты явно покрывают сценарий «Save ok, Publish error → не возвращаем ошибку клиенту». |
| D-09 | Подписка на новые комнаты после connect | НЕ авто-подписывается. Подписка на room: применяется только при connect; для появления подписки на новую комнату — reconnect. | (a) Hub слушает `member.added` event и автоподписывает существующие WS-коннекты пользователя | Усложняет жизненный цикл подписки и требует ещё одного порта. MVP-сценарий: пользователь джоинится через REST → клиент инициирует reconnect → события идут. Будущее расширение — добавить «Hub.OnUserMembershipChanged» с явной обработкой. |
| D-10 | Cursor pagination | По `message_id` (UUID), но индекс — по `(channel_id, created_at DESC, id DESC)`. Запрос: `WHERE channel_id = .. AND (created_at, id) < (SELECT created_at, id FROM messages WHERE id = $before) ORDER BY created_at DESC, id DESC LIMIT n` | (a) cursor по `created_at` (риск дублей на одинаковом времени); (b) page+offset (плохо масштабируется); (c) keyset по `created_at + id` без преобразования cursor → row | UUID-cursor стабилен, не зависит от часов клиента. Один дополнительный sub-SELECT в БД — допустимо для MVP. Альтернативу с keyset (явная передача `(created_at, id)` в URL) рассмотрим, если профилировка покажет проблему. |
| D-11 | Origin policy для WS | Использовать те же `cfg.CORSAllowedOrigins()`, что для HTTP CORS. nhooyr `Accept` принимает `OriginPatterns` — конвертация из CORS-config. `InsecureSkipVerify=false`. | (a) отдельный env `WS_ALLOWED_ORIGINS`; (b) `InsecureSkipVerify=true` для упрощения | Единый конфиг проще. Браузеры всегда шлют Origin для WS — same origin policy сохраняется. |
| D-12 | Внешняя зависимость `nhooyr.io/websocket` | Добавляется в `go.mod` | (a) собственный реализатор RFC 6455 (overkill); (b) gorilla/websocket; (c) coder/websocket (форк) | Зафиксировано пользователем (см. ответы AskUserQuestion). Минимальный API, поддерживает `context.Context` нативно, не требует ручной работы с deadlines. |
| D-13 | `chat/domain` имеет собственные `ChannelID`, `UserID`, `RoomID` (не импортирует `channel/domain` / `auth/domain` / `room/domain`) | Свои VO в `internal/chat/domain/` (по аналогии с `channel/domain` имеет собственные `UserID`, `RoomID`) | (a) импортировать чужие VO; (b) общий пакет VO в `internal/sharedids/` | `chat/domain` — чистый. Зависимость только от stdlib + uuid. Маппинг между uuid'ами — на границе с usecase/repo. Дублирование 3-х однотипных файлов — приемлемая цена за изоляцию (повторяет паттерн channel, room). |
| D-14 | Длина сообщения и кодировка | `1..4000` рун (Unicode code points), не байт. `TrimSpace` перед валидацией. Whitelist символов: всё кроме `unicode.IsControl()` за исключением `\n`, `\r`, `\t`, и категория `Cf` запрещена (anti-spoofing) | (a) лимит в байтах; (b) разрешить все символы | Дискорд-подобный лимит. Лимит в рунах справедливее для не-латиницы. Anti-spoofing — повтор паттерна `channel/domain/channel_name.go:24-28`. |
| D-15 | Шаблон именования файла транспорта WS | `internal/chat/transport/ws/handler.go` + `event_dto.go` + `routes.go` (если решим использовать chi для регистрации) + `setup_test.go` | (a) `transport/websocket/` (длиннее); (b) `delivery/ws/` (не наш стиль) | Зеркалит `internal/chat/transport/http/`. Регистрация роута: `httpchat.RegisterWSRoute(r chi.Router, deps WSDeps)`, монтируется отдельно от REST-роутов. |

## Риски и митигация

| Риск | Влияние | Митигация |
|---|---|---|
| Утечка горутин при медленных клиентах | High | `Conn` имеет `WriteDeadline` (5s); при таймауте hub закрывает conn и анмаунтит подписки. Покрывается тестом `Hub_SlowClient_GetsDisconnected`. |
| Memory blowup при множестве пустых broadcast'ов | Medium | Hub держит подписки в `map[Topic]map[ConnID]*Conn`; при отсутствии подписчиков `Publish` — no-op без аллокаций фрейма. Сериализация event'а — один раз перед итерацией по подписчикам. |
| Гонка subscribe/publish | Low | Hub-операции под `sync.RWMutex`. `Subscribe` берёт `Lock`, `Publish` — `RLock` + по копии слайса подписчиков. Покрывается race-test'ами. |
| `member.joined` publish дёргается до commit'а транзакции | Medium | В `room/usecase.JoinByCode` Publish вызывается ПОСЛЕ возврата успеха от `Add(membership)`. Поскольку в нашем коде нет явного `BeginTx`, операция атомарна сама по себе. Если в будущем введём UoW — Publisher вынесем в after-commit hook. |
| Race на close при graceful shutdown | Medium | `Hub.Shutdown(ctx)` — single-call под `sync.Once`. `Conn.Close` — idempotent. Тесты для повторного `closeFn()`. |
| Отсутствие observability (метрики broadcast latency, queue size) | Low | Логирование на каждый publish с request_id (если есть в контексте). Метрики оставляем на фазу 3.2 / observability-инициативу. |
| Размер фрейма (DoS через гигантское сообщение) | Medium | `nhooyr.io/websocket` имеет `SetReadLimit`; задаём `64 KB` (запас над лимитом 4000 рун ≈ 16 KB UTF-8). Превышение → close 1009. |
| WS-токен в query попадает в access-log | High (security) | В `pkg/httpx/middleware.Logger` нужно вырезать `token` из логируемого URL для пути `/api/v1/ws`. Добавляем явный filter — см. `04-testing.md` тест-кейс `Logger_StripsTokenFromWSPath`. |
| `mass member.joined` при массовом invite | Low | На каждый JoinByCode — один publish одной комнате. Подписчиков мало (только активные WS-коннекты этой комнаты). Backpressure не требуется. |

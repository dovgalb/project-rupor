# Решения по схеме `refresh_tokens`

## Решения

| # | Решение | Выбор | Альтернативы | Обоснование |
|---|---------|-------|--------------|-------------|
| 1 | Хранить refresh-токены в БД? | Да, в таблице `refresh_tokens` | Stateless JWT (только подпись + TTL, без таблицы) | Утверждено пользователем. БД-хранение даёт возможность отзыва конкретной сессии (logout, ban, ротация) и инвариант «один токен — один use». Stateless вариант не позволяет инвалидировать выпущенный токен до истечения срока. |
| 2 | Что писать в столбец токена | `token_hash` — `sha256(token)` (32 байта) | (a) Сам токен; (b) JTI внутри JWT + таблица отозванных | Утверждено пользователем. (a) утечка БД = утечка всех активных сессий. (b) добавляет JWT-парсинг на каждый refresh и усложняет инвариант ротации. Хеш плюс ротация — стандартный паттерн (RFC 6819 §5.2.2.3) и совместим с проектом, где bcrypt уже используется для паролей (задача 1.3). |
| 3 | Тип столбца `token_hash` | `bytea NOT NULL` + `CHECK (octet_length(token_hash) = 32)` + `UNIQUE` | (a) `text` (hex/base64); (b) `char(64)` | sha256 — это 32 сырых байта; `bytea` не требует кодирования, экономит место и точно описывает семантику. `CHECK` фиксирует длину как инвариант БД и защищает от записи неправильных значений в будущем (например, sha1/md5). `text` потребовал бы фиксации кодировки (hex vs base64) и удвоил бы размер. |
| 4 | Тип первичного ключа | `uuid PRIMARY KEY DEFAULT gen_random_uuid()` | `bigserial`, клиентская генерация | Согласуется с `users.id` и общим решением 1 в `docs/users_table/03-decisions.md:12`. `pgcrypto` уже подключён `0001_init`. |
| 5 | Внешний ключ `user_id` | `uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE` | `ON DELETE RESTRICT` / без FK | `CASCADE` корректно отражает инвариант: удаление пользователя обязано инвалидировать все его сессии. RESTRICT блокировал бы удаление пользователя при наличии токенов. Отсутствие FK ослабило бы целостность ради сомнительного выигрыша. |
| 6 | Имя FK | Дефолтное Postgres: `refresh_tokens_user_id_fkey` | Кастомное (например, `auth_refresh_tokens_user_fk`) | Дефолтные имена детерминированы и предсказуемы; согласуется с решением 6 в `docs/users_table/03-decisions.md:17`. |
| 7 | Уникальность `token_hash` | `UNIQUE` (имя — дефолт `refresh_tokens_token_hash_key`) | `CREATE UNIQUE INDEX` отдельно | `UNIQUE` достаточно: Postgres создаёт b-tree индекс автоматически; имя ограничения = имя индекса. Отдельный `CREATE INDEX` дал бы два одинаковых индекса. То же решение, что и для `users_email_key` (`docs/users_table/03-decisions.md:18`). Имя `refresh_tokens_token_hash_key` ожидается в задаче 1.3 для маппинга unique-violation в доменную ошибку (`prompts/RepoModel.txt:138-140`). |
| 8 | Индекс на `user_id` | Отдельный `CREATE INDEX refresh_tokens_user_id_idx ON refresh_tokens(user_id)` | Не создавать; полагаться на FK | Postgres **не создаёт** индекс под FK-столбец автоматически. Запросы «все токены пользователя» (logout-all, ротация) и каскадное удаление при `DELETE FROM users` без индекса дадут seq-scan. Индекс — обязательная инфраструктура под FK-столбец. |
| 9 | Состояние «активный/отозван» | Столбец `revoked_at timestamptz NULL` (NULL = активный) | (a) булев `is_revoked`; (b) отдельная таблица `revoked_tokens` | Один nullable-столбец одновременно фиксирует **факт** отзыва и **момент** (нужен для аудита и cleanup). Bool теряет момент. Отдельная таблица — overkill для MVP. Запрос активных токенов: `WHERE revoked_at IS NULL AND expires_at > now()`. |
| 10 | Партиальный индекс под активные токены | Не добавлять | `CREATE INDEX ... WHERE revoked_at IS NULL` | Партиальный индекс — оптимизация под нагрузку, которой в MVP нет. Уникальный индекс на `token_hash` уже даёт O(log n) lookup. Добавим, если профиль покажет seq-scan на active-фильтрах в проде. |
| 11 | Столбец `expires_at` | `timestamptz NOT NULL` без default | (a) DEFAULT `now() + interval '30 days'`; (b) `int8` (unix nano) | TTL — это политика приложения (задача 1.3, конфиг через env), а не схемы. Default «зашитый» в миграцию был бы неявной зависимостью. `timestamptz` — единый тип времени в проекте (см. решение 5 в `docs/users_table/03-decisions.md:16`). |
| 12 | Столбец `created_at` | `timestamptz NOT NULL DEFAULT now()` | Передавать из приложения | Согласуется с `users.created_at` (`docs/users_table/03-decisions.md:16`). Default снимает класс багов «забыли заполнить». |
| 13 | `device_id` / `user_agent` / `ip` | Не добавлять | Поля под аудит сессий | Не входит в scope MVP-плана. Правило `CLAUDE.md` «не проектировать под гипотетические требования». Если потребуется — отдельная миграция. |
| 14 | Soft-delete vs hard-delete отозванных | `revoked_at` без удаления строки | `DELETE FROM refresh_tokens WHERE revoked_at IS NOT NULL` | Сохранение строк нужно для аудита и анти-replay (UNIQUE по `token_hash` блокирует переиспользование даже отозванного хеша). Cleanup истёкших/отозванных — отдельная задача (cron или background job в фазе 1.3+). |
| 15 | Имя slug миграции | `0003_refresh_tokens` | `0003_create_refresh_tokens` / `0003_auth_tokens` | Соответствует стилю `0001_init` / `0002_users` (короткий slug по существу таблицы). Префикс `0003` — следующий свободный (см. research, `## Состояние ветки и Git`). |
| 16 | Изменения вне `migrations/` | Никаких | Заодно настроить `sqlc.yaml`, добавить queries | `sqlc.yaml` пуст (`sqlc.yaml:1-2`); его настройка и запросы — задача 1.3. Согласуется с решением 12 в `docs/users_table/03-decisions.md:23`. |

## Риски и митигация

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Коллизия `sha256` теоретически возможна, но `UNIQUE` сделает `INSERT` падающим вместо silent overwrite | Low | sha256 даёт 2^128 birthday-bound коллизии — практически недостижимо при разумных объёмах. `UNIQUE` гарантирует, что коллизия не приведёт к подмене сессии: задача 1.3 регенерирует токен и повторит INSERT. |
| Утечка БД — оппонент видит `token_hash`, но не сам токен | Low | По хешу нельзя восстановить токен (sha256 невыполнима в обратную сторону для случайных 256-битных входов). Атакующий не может выпустить новый access по хешу. |
| Неудалённый `citext`-extension от `0002_users` сейчас никак не нужен `refresh_tokens` | Low | Не используется в этой миграции; не трогаем. Down-миграция этой фичи дропает только свои объекты. |
| Down-миграция упадёт, если есть данные с FK | Low | `DROP TABLE refresh_tokens` снимет FK сам; зависимостей со стороны других таблиц на `refresh_tokens` нет. Down предназначен для dev-отката (см. `docs/users_table/03-decisions.md`, риск «Down-миграция падает, если в БД уже есть данные»). |
| Будущая фича потребует партиальный индекс / partition по `expires_at` | Low | Это норма; добавим отдельной миграцией, когда появится профиль нагрузки. Решения 10 и 14 фиксируют сознательный отказ от prematurity. |
| Каскадное удаление пользователя удалит большое число строк `refresh_tokens` без индекса по `user_id` | Medium | Решение 8 — обязательный индекс `refresh_tokens_user_id_idx`. Без него `ON DELETE CASCADE` будет делать seq-scan. |
| Имя `refresh_tokens_token_hash_key` усечётся Postgres при превышении 63 символов | Low | Длина 32 символа — заметно меньше `NAMEDATALEN`. Проверяется глазом через `\d refresh_tokens` после `migrate-up`. |

## Open Questions

- [x] Хранить refresh в БД или ограничиться stateless JWT?
  - **Ответ:** в БД. Решение 1.
- [x] Hash, raw token или JTI?
  - **Ответ:** hash + ротация. Решения 2–3, 9, 14.
- [x] Тип `token_hash` — `text` или `bytea`?
  - **Ответ:** `bytea` + `CHECK (octet_length = 32)`. Решение 3.
- [x] FK на `users` нужен?
  - **Ответ:** да, `ON DELETE CASCADE`. Решение 5.
- [x] Индекс на `user_id`?
  - **Ответ:** отдельный b-tree индекс. Решение 8 (Postgres не создаёт индекс под FK-столбец).
- [x] Партиальный индекс под активные токены?
  - **Ответ:** не сейчас. Решение 10 — добавим по профилю нагрузки.
- [x] Поля аудита (device_id / user_agent / ip)?
  - **Ответ:** не в MVP. Решение 13.
- [x] Cleanup отозванных/истёкших токенов?
  - **Ответ:** не входит в scope этой фичи. Реализация — задача 1.3+ (cron / background job). Решение 14.
- [ ] TTL refresh-токена как параметр конфига или константа?
  - **Отложено:** решается в задаче 1.3 при проектировании `TokenIssuer` (`general_plan.md:109`); миграция от этого решения не зависит.
- [ ] Лимит количества активных сессий на пользователя?
  - **Отложено:** в MVP-плане не требуется. Если появится — решается на уровне usecase (например, отзыв самой старой при выпуске N+1-й).
